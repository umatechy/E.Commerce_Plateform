# ADR-003 — Physical Database Schema and ID Conventions

1. **ADR ID:** ADR-003
2. **Title:** Physical Database Schema and ID Conventions
3. **Status:** PROPOSED
4. **Date:** 2026-09-18
5. **Decision Owners:** Database Engineer / Senior Software Architect, pending Project
   Owner approval

---

## 6. Context

The Project Bible (§11 Data Architecture) and Module Blueprints define **conceptual**
data models (Tenant, User, Role, Permission, Package, Entitlement, Product, Order, etc.)
with required behaviors (audit fields, soft deletion where justified, tenant-aware
indexing) but deliberately do not specify physical column names, types, or index
definitions — confirmed absent across all 35 module files during the readiness review.
This ADR establishes the **conventions** (not the full schema) so that every table
created from Milestone 0 onward is consistent.

## 7. Problem Statement

Without agreed conventions, different tables risk inconsistent primary-key strategies,
inconsistent tenant-column naming, missing tenant-aware indexes, and inconsistent
money/status representations — each of which is expensive to fix once commerce data
exists.

## 8. Decision

**Primary keys:** Every table uses an auto-increment `BIGINT UNSIGNED` internal primary
key named `id`, for join/index performance on MySQL InnoDB. This is the *internal*
identifier and is never exposed in public URLs or the Developer API.

**Public identifiers:** Every table that is ever referenced externally (in a URL, an
API response, an invoice, a customer-facing order number) additionally has a `ULID`
(26-char, lexicographically sortable) stored in a dedicated indexed `public_id` column,
generated at creation time. ULID is chosen over UUIDv4 because its sortability keeps
InnoDB clustered-index insert performance good (unlike random UUIDv4), while still being
non-guessable and safe to expose. Human-facing business identifiers (order number,
invoice number) are separate, sequential-per-tenant display values (e.g.
`ORD-{store_short_code}-000123`), generated by a tenant-scoped sequence — never the
same value as the internal `id` or `public_id`.

**Tenant ID:** Every tenant-owned table has a `store_id BIGINT UNSIGNED NOT NULL`
foreign key to `stores.id`, matching ADR-001's global-scope mechanism. Platform-only
tables (e.g. platform-level settings) have no `store_id` column at all — its absence is
itself meaningful and reviewed, not defaulted to nullable-and-ignored.

**Foreign keys:** All foreign keys are declared as real MySQL foreign-key constraints
(InnoDB), not application-only relationships, to guarantee referential integrity at the
database layer as a second line of defense beyond Eloquent. Default `ON DELETE`
behavior is `RESTRICT` for financial/audit-relevant tables (orders, payments, invoices)
and `CASCADE` only for genuinely dependent child data (e.g. `order_items` under
`orders`) where the parent's soft-delete/archival already governs lifecycle.

**Naming conventions:**
- Tables: `snake_case`, plural (`stores`, `products`, `order_items`).
- Columns: `snake_case`, singular (`store_id`, `created_at`).
- Pivot/relationship tables: alphabetised singular model names joined by underscore
  (`role_user`, `product_category`).
- Indexes: `idx_{table}_{columns}`; unique constraints: `uniq_{table}_{columns}`;
  foreign keys: `fk_{table}_{column}`.

**Tenant-aware indexing:** Every composite index that supports a tenant-scoped query
lists `store_id` **first** (e.g. `idx_orders_store_id_status_created_at`), so MySQL can
use the index prefix efficiently for the always-present tenant filter from ADR-001
Layer 3.

**Unique constraints:** Uniqueness that is business-scoped per tenant (e.g. a product
SKU) is declared as a **composite** unique constraint `(store_id, sku)`, never a global
unique constraint on `sku` alone — two different stores may legitimately use the same
SKU value.

**Timestamps:** Every table has `created_at`, `updated_at` (Laravel default). Tables
representing state transitions relevant to audit (orders, payments, subscriptions) also
carry explicit event timestamps (e.g. `paid_at`, `shipped_at`, `cancelled_at`) rather
than inferring state-change time from `updated_at` alone.

**Soft deletes:** Applied per Module guidance ("where business/audit integrity
requires it") using Laravel's standard `deleted_at` nullable timestamp — applied to:
products/catalog (Module 06 §82), customers, orders, invoices, and any entity subject
to legal/financial retention (Module 32 §43). **Not** applied to purely transient data
(cart items, sessions, cache-backed rows), which use hard deletes.

**Audit fields:** Tenant-owned mutable business records additionally carry
`created_by`/`updated_by` (nullable `BIGINT UNSIGNED` referencing `users.id`, `NULL`
allowed for system/automated actions) in addition to the append-only audit log
(Module 32) — the column gives fast "who last touched this row" access; the audit log
gives the full history.

**JSON columns:** Permitted only for genuinely schema-flexible, non-relational,
non-queried-by-value data (e.g. theme configuration blobs, webhook payload snapshots,
notification template variables). Any field that is filtered, joined, or reported on is
a real column, never buried in JSON.

**Enum strategy:** Application-level enums (PHP backed enums) are used for status/type
fields, persisted as a `VARCHAR` (not MySQL native `ENUM`, which is painful to alter
under load) with a matching `CHECK` constraint where MySQL 8.0 supports it, so both the
application and the database enforce valid values.

**Money/currency storage:** All monetary amounts are stored as `BIGINT` **minor units**
(e.g. cents/paisa) — never `FLOAT`/`DOUBLE`, and never `DECIMAL` alone without a defined
currency — paired with a `currency` `CHAR(3)` (ISO 4217) column on the same row. This
avoids floating-point rounding errors and directly supports the future multi-currency
Premium feature (Module 04, Bible §17).

**Decimal precision:** Non-money numeric fields that need fractional precision (e.g.
weight, dimensions, tax rates) use `DECIMAL(precision, scale)` sized explicitly per
field, never `FLOAT`.

**Status fields:** Every status/state field is a backed enum-as-string column (see
above) plus, where the entity has a meaningful lifecycle (orders, subscriptions,
payments), a companion `*_history` or event-sourced audit trail (see ADR-004) rather
than only the current value — so past states are never silently lost.

**Optimistic locking:** Applied via a `BIGINT` `lock_version` column, incremented on
every update, on tables subject to concurrent contention identified in the
documentation — specifically **inventory/stock quantity rows** (Module 08 concurrency
requirement) and **payment/order state transition rows** — to prevent lost-update race
conditions without holding long database locks.

**Quantities:** Stock/inventory quantities and order-line quantities are stored as
`INT UNSIGNED` (whole units) unless a module explicitly documents fractional units
(e.g. weight-based products), in which case `DECIMAL(precision, scale)` is used with an
explicit unit column — never a bare float.

**Percentages:** Stored as `DECIMAL(5,2)` representing a 0.00–100.00 range (e.g.
discount percentage, tax rate), never as a raw float and never pre-divided into a 0–1
fraction in the database (application code converts at the presentation layer only).

**Nullable fields:** A column is nullable only when "unset" is a genuinely valid,
distinct business state from any concrete value (e.g. `shipped_at IS NULL` = not yet
shipped). Foreign keys are nullable only when the relationship is genuinely optional
(e.g. `orders.coupon_id` may be null); tenant (`store_id`) and audit (`created_at`)
columns are never nullable on tenant-owned tables.

**Migration conventions:** One migration = one reviewable, reversible change. Every
migration implements both `up()` and `down()` meaningfully (no empty `down()` on a
structural change) per Bible §38 / Master Dev Prompt "reversible where practical."
Migration file names follow Laravel's default timestamp-prefixed convention plus a
descriptive snake_case suffix (`..._create_orders_table.php`,
`..._add_lock_version_to_inventory_items_table.php`). Destructive migrations (dropping
a column/table) are never bundled with additive changes in the same migration, so a
rollback of one does not risk the other.

**High-volume tables:** Tables expected to grow fastest (order items, audit logs, outbox
events, notifications) are designed from the start with lean row width, no unnecessary
JSON, and indexes limited to actually-queried access patterns (over-indexing slows
writes on exactly these tables). Partitioning/archival strategy for these tables is a
Module 23 (Backup/Restore) and Module 35 (Future Expansion) concern, not a Milestone 0
concern, but the leading-`store_id` index convention (§8) keeps a future per-tenant
partitioning path open.

**Reporting indexes:** Read-heavy reporting/analytics queries (Module 22) get their own
purpose-built composite indexes (e.g. `idx_orders_store_id_created_at_status` for
"orders by store in a date range with a given status") rather than reusing a
transactional index opportunistically — added deliberately per report, reviewed for
write-cost impact on the underlying table.

**Database security:** Database credentials are never hard-coded (`.env`-only, per
Milestone-0 §7); the application's MySQL user has no `DROP`/`SUPER` privileges in
production; sensitive columns that must be stored (e.g. tokenized payment references,
never raw card data per Module 31 §17.2) use Laravel's built-in encrypted-cast
mechanism at the application layer in addition to disk-level/at-rest encryption
provided by the hosting platform. Access to production database credentials is
restricted and audited per Module 32.

**Backup implications:** Every convention in this ADR (soft-deletes, audit fields,
explicit event timestamps) is chosen to make Module 23's point-in-time
backup/restore meaningful — e.g. soft-deleted rows remain restorable, and audit
fields let a restored dataset be reconciled against the audit log for consistency
verification after a restore.

## 9. Detailed Implementation Rules

- No table is created without: `id`, tenant column (if tenant-owned), timestamps, and a
  documented index plan reviewed against this ADR before migration is written.
- No migration introduces a native MySQL `ENUM` type.
- No monetary column is ever `FLOAT`/`DOUBLE`.
- No globally-unique constraint is placed on a business value (SKU, coupon code, etc.)
  without confirming with the relevant Module Blueprint whether the value is meant to be
  tenant-scoped or platform-wide.

## 10. Alternatives Considered

- **A — UUIDv4 primary keys everywhere:** Rejected as the primary key (InnoDB clustered-
  index fragmentation under random insert order at scale); retained only as the
  externally-visible `public_id` via ULID, which is sortable and avoids this problem.
- **B — Native MySQL `ENUM` columns:** Rejected; schema changes to add a new enum value
  require a full `ALTER TABLE`, which is risky at scale and contradicts the "safe,
  reversible migrations" rule (Bible §38, Master Dev Prompt §Database Safety).
- **C — `DECIMAL` for money:** Rejected as the primary storage type in favor of integer
  minor-units, which avoids any rounding ambiguity across currencies and payment
  gateway integrations (Module 12); `DECIMAL` remains acceptable for non-money
  fractional fields.
- **D (Selected) — the conventions above**, chosen specifically because they are the
  common, well-understood defaults for a MySQL-backed, multi-tenant commerce SaaS at the
  platform's target scale, and they directly support ADR-001's tenant-aware indexing
  requirement.

## 11. Why Alternatives Were Not Selected

Each rejected alternative either creates a known, well-documented operational problem at
scale (UUID PK fragmentation, ENUM alterability) or a category of financial bug (float/
decimal-only money) that is disproportionately expensive to fix after real transaction
data exists.

## 12. Security Implications

Internal `BIGINT` IDs are never exposed externally (only `public_id`/business numbers
are), reducing enumeration/IDOR risk as a second layer beneath ADR-001's tenant scoping.
Foreign-key constraints at the database layer prevent orphaned/dangling references even
if an application-layer bug is introduced.

## 13. Multi-Tenant Implications

This ADR is the physical counterpart to ADR-001: every tenant-owned table's `store_id`
placement and indexing directly implements ADR-001 Layer 3's performance and integrity
requirements.

## 14. Database Implications

This ADR **is** the database-implications document; it governs Milestone 0 — Step 0.4
directly (Tenant/Store, User, Role, Permission, Package, Entitlement tables).

## 15. API Implications

API responses (both Surfaces from ADR-002) serialize `public_id`/business identifiers,
never the internal `id`, consistent with §8 above.

## 16. Testing Implications

- Migration tests confirming every tenant-owned table has a `store_id` foreign key and a
  leading `store_id` composite index.
- A schema-lint check (part of CI, Step 0.11) flagging any new `FLOAT`/`DOUBLE` column on
  a table matched against a money-related naming pattern (`*_amount`, `*_price`,
  `*_total`) for manual review.
- Optimistic-locking concurrency tests for inventory stock decrement under simulated
  concurrent checkout.

## 17. Operational Implications

Consistent naming makes ad-hoc production debugging and reporting queries predictable
across all 35 modules' tables.

## 18. Scalability Implications

Leading-`store_id` composite indexes keep per-tenant query cost roughly constant as
total platform row count grows, which is the key scalability property required for a
shared-database multi-tenant design.

## 19. Migration / Rollout Considerations

These conventions apply from the very first migration (Milestone 0 — Step 0.4) onward.
No retrofitting is needed if followed from the start; retrofitting would be required
(and costly) if commerce tables are built before this ADR is accepted.

## 20. Consequences

**Positive:** Predictable, reviewable schema across 35 modules; avoids three well-known
classes of production bugs (UUID PK fragmentation, ENUM alteration pain, float-money
rounding errors); directly supports ADR-001's performance model.

**Negative / trade-offs:** Slightly more verbose migrations (explicit `public_id`
generation, explicit currency columns) than the naive equivalent; requires developer
discipline to follow the naming convention consistently (mitigated by a documented,
reviewable standard).

## 21. Future Reconsideration Conditions

Reconsider if MySQL is ever replaced (out of scope for now — Meilisearch is a search-
only addition, not a primary-database replacement), or if a specific module's data
shape genuinely cannot fit these conventions (to be raised as a module-specific
exception request, not a silent deviation).
