12. IMPLEMENTATION STYLE
====================================================================

Prefer:

- Small coherent changes
- Reusable services
- Clear domain boundaries
- Explicit interfaces/contracts
- Strong validation
- Testable business logic
- Dependency injection where appropriate
- Provider adapters
- Idempotent workflows
- Background jobs for long operations
- Structured logging
- Correlation IDs
- Configuration registry
- Centralized authorization
- Centralized entitlement checks

Avoid:

- Giant controllers
- Giant services
- Duplicated business logic
- Copy-pasted package implementations
- Hard-coded secrets
- Hard-coded environment assumptions
- Client-authoritative business rules
- Unnecessary framework changes
- Unnecessary rewrites
- Temporary hacks presented as permanent architecture

====================================================================
13. DATABASE RULES
====================================================================

Use safe migrations.

Before schema changes:

1. Understand existing schema.
2. Identify data dependencies.
3. Identify indexes/constraints.
4. Identify production risk.
5. Plan migration.
6. Test migration.
7. Consider rollback/recovery.
8. Document the change.

Never casually:

- Drop tables
- Drop columns containing data
- Truncate data
- Replace production schema
- Perform mass updates without safeguards

Tenant-scoped uniqueness must be implemented correctly.

Historical orders and financial records must preserve required historical truth.

====================================================================
14. API DEVELOPMENT RULES
====================================================================

Every sensitive endpoint requires:

- Authentication
- Tenant resolution where applicable
- Authorization
- Input validation
- Business-rule validation
- Entitlement check where applicable
- Rate limiting where appropriate
- Audit where required
- Structured errors
- Request/correlation ID

Use API versioning.

Do not break an existing API silently.

Breaking changes require versioning or a documented migration strategy.

====================================================================
15. API ERROR STANDARD
====================================================================

Use a stable structured error model similar to:

{
  "code": "STABLE_ERROR_CODE",
  "message": "Safe message",
  "details": {},
  "requestId": "request-id"
}

Never expose:

- Stack traces
- SQL
- Secrets
- Internal tokens
- Sensitive infrastructure details

====================================================================
16. IDEMPOTENCY RULE
====================================================================

Implement idempotency for retry-sensitive operations such as:

- Checkout
- Order creation
- Payment initiation
- Refunds
- Subscription changes
- Invoice creation
- Webhook processing
- Provisioning
- Bulk operations

Never blindly retry financial operations.

====================================================================
17. PAYMENT DEVELOPMENT RULES
====================================================================

Use provider adapters.

Core domain must not depend directly on one payment provider.

Payment flow:

Create Payment Attempt
 ->
Provider Interaction
 ->
Verified Provider Result
 ->
Payment State
 ->
Order State

Browser redirects are NOT authoritative payment confirmation.

Webhook verification is mandatory where providers support webhooks.

Never store raw card data unless a specifically approved compliant
architecture requires it.

====================================================================
18. WEBHOOK RULES
====================================================================

Every webhook implementation must consider:

- Signature verification
- Timestamp validation
- Replay protection
- Event ID
- Idempotency
- Duplicate delivery
- Retry
- Dead-letter handling
- Tenant/integration mapping
- Audit
- Monitoring

A webhook must not execute business effects twice because a provider retries it.

====================================================================
19. INVENTORY RULES
====================================================================

Inventory is server-authoritative.

For checkout:

- Re-read product
- Re-read availability
- Validate quantity
- Reserve stock safely
- Handle concurrency
- Expire/release reservation safely
- Finalize stock movement at the correct order state

Test concurrent checkout scenarios.

====================================================================
20. ORDER RULES
====================================================================

Orders are historical business records.

Do not let future product changes silently rewrite historical order facts.

Order status transitions must be explicit.

Invalid transitions must be rejected.

Order creation must safely coordinate:

- Customer
- Cart
- Inventory
- Promotion
- Shipping
- Tax
- Payment
- Order
- Notifications
- Analytics

====================================================================
21. SECURITY-FIRST DEVELOPMENT
====================================================================

For every feature ask:

1. Who can call it?
2. Which tenant does it belong to?
3. Which object is being accessed?
4. Which fields may be changed?
5. Which package allows it?
6. What happens if the request is replayed?
7. What happens if it is duplicated?
8. What happens if the provider fails?
9. What data appears in logs?
10. What happens if the user changes an ID?
11. What happens if the user removes a field?
12. What happens if the user sends unexpected values?
13. What happens under concurrency?
14. What happens after downgrade/suspension?
15. What happens after account/store closure?

25. BACKGROUND JOB RULES
====================================================================

Jobs must support:

- Retry policy
- Idempotency
- Timeout

- Correlation ID
- Failure handling
- Dead-letter handling where appropriate

====================================================================
26. CACHE RULES
====================================================================

Every tenant-specific cache key must contain sufficient tenant/store scope.

Never use:

cache["products"]

for tenant-specific product data.

Prefer a properly scoped strategy such as:

cache["tenant:{tenantId}:store:{storeId}:products:{key}"]

Actual implementation may differ but must preserve the isolation principle.
