1. MODULE PURPOSE
--------------------------------------------------------------------
Module 18 provides the Core Animation, Motion, Transition, Gesture,
Interaction, and Micro-Interaction System for the Umar Techy
Multi-Tenant E-Commerce Platform.

The module provides a reusable, configuration-driven motion engine
that allows each store to have a controlled interaction style while
remaining on the same core platform and codebase.

The system must support:

- Page transitions.
- Component transitions.
- Hover interactions.
- Press interactions.
- Scroll-based effects.
- Reveal animations.
- Product interactions.
- Cart feedback.
- Loading states.
- Skeleton transitions.
- Modal/drawer transitions.
- Toast notifications.
- Micro-interactions.
- Gesture foundations.
- Reduced-motion support.
- Device-aware behavior.
- Performance safeguards.
- Theme-level animation profiles.
- Store-specific animation configuration.
- Package-based animation entitlements.

Core principle:

ONE CORE MOTION ENGINE
        +
CONFIGURATION-DRIVEN ANIMATION PROFILES
        +
THEME INTEGRATION
        +
TENANT-SPECIFIC SETTINGS
        +
PERFORMANCE & ACCESSIBILITY SAFEGUARDS

No tenant-specific animation source-code forks are permitted.


2. PRIMARY OBJECTIVES
--------------------------------------------------------------------
The module shall:

1. Provide a reusable animation and interaction architecture.
2. Define centralized motion tokens.
3. Support configurable animation profiles.
4. Integrate with Module 17 Theme, Branding & Design System.
5. Provide consistent component motion behavior.
6. Support storefront page transitions.
7. Support micro-interactions for commerce actions.
8. Support reduced-motion accessibility.
9. Respect device and performance capabilities.
10. Prevent animation from blocking business operations.
11. Support mobile and desktop interaction differences.
12. Provide safe scroll/reveal animation foundations.
13. Provide gesture foundations without coupling to business logic.
14. Support package-based animation capabilities.
15. Support preview and publishing of animation configuration.
16. Preserve previous animation configuration for rollback.
17. Prevent cross-tenant configuration leakage.
18. Provide observability and performance diagnostics.
19. Support future theme marketplace compatibility.
20. Provide comprehensive automated testing.

--------------------------------------------------------------------

Other modules remain authoritative for their business domains.


4. MOTION DESIGN PRINCIPLES
--------------------------------------------------------------------
The animation system must follow these principles:

1. Purposeful.
2. Fast.
3. Consistent.
4. Accessible.
5. Interruptible.
6. Performance-conscious.
7. Device-aware.
8. Progressive enhancement.
9. Non-blocking.
10. Reversible where practical.

Animations must communicate:

- State changes.
- Hierarchy.
- Continuity.
- Feedback.
- Focus.
- Spatial relationships.

Animations must not exist merely for visual decoration when they
harm usability or performance.

6. DURATION SYSTEM
--------------------------------------------------------------------
Provide semantic duration presets such as:

- Instant.
- Very fast.
- Fast.
- Normal.
- Slow.

Typical guidance:

Instant:
Immediate state feedback.

Fast:
Button, hover, small UI changes.

Normal:
Cards, drawers, menus, standard transitions.

Slow:
Large visual transitions or deliberate hero effects.

Exact timing values must be centrally controlled and performance
tested.

--------------------------------------------------------------------

- Linear.
- Standard.
- Ease-in.
- Ease-out.
- Ease-in-out.
- Emphasized.
- Spring foundation.

Theme profiles may choose different curves.

The system should avoid excessive bouncing or elastic behavior unless
explicitly configured.

11. PAGE TRANSITIONS
--------------------------------------------------------------------
Support optional page transitions such as:

- Fade.
- Fade + slide.
- Scale/fade.
- Shared-element foundation.
- Crossfade.

Rules:

1. Page transitions must not delay navigation unnecessarily.
2. They must be disabled or simplified on low-performance devices.
3. Reduced-motion users must receive an appropriate alternative.
4. Browser navigation/back/forward behavior must remain correct.
5. Deep links must work without requiring an animation state.


12. COMPONENT TRANSITIONS

Reusable transitions may include:

- Expand/collapse.
- Show/hide.
- Fade.
- Slide.
- Scale.
- Height/width transition.
- Drawer entry/exit.
- Modal entry/exit.
- Tooltip/popover transition.

Transitions must handle:

- Interruptions.
- Rapid state changes.
- Component unmounting.
- Route changes.
- Error states.


13. HOVER INTERACTIONS
--------------------------------------------------------------------
Desktop-capable devices may support:

- Product image swap.
- Card elevation.
- Button elevation.
- Underline animation.
- Icon movement.
- Subtle scale.
- Color transition.

Hover interactions must not be the only way to discover functionality.

Touch devices must not depend on hover behavior.


14. PRESS / TAP FEEDBACK
--------------------------------------------------------------------
Interactive elements may support:

- Scale-down feedback.
- Ripple foundation.
- Opacity change.
- Icon feedback.
- Loading transition.

Feedback must be brief and must not alter business state incorrectly.

Double-tap or repeated tap must not cause duplicate financial or
order operations.

--------------------------------------------------------------------
Product cards may support:

- Image transition.
- Hover elevation.
- Wishlist feedback.
- Add-to-cart feedback.
- Quick-view transition.
- Badge animation.

Animation must not hide:

- Product name.
- Price.
- Sale information.
- Stock state.

16. ADD-TO-CART FEEDBACK
--------------------------------------------------------------------
Support visual feedback such as:

- Button state change.
- Cart icon count transition.
- Small confirmation animation.
- Toast.
- Product image movement foundation.

The animation layer must respond only to confirmed UI/business
events and must never imply a successful purchase before the

17. WISHLIST FEEDBACK
--------------------------------------------------------------------
Support:

- Icon transition.
- Favorite state animation.
- Toast feedback.
- Loading state.

Animation must distinguish:

- Request started.
- Success.
- Failure.

Wishlist business logic remains outside Module 18.


18. LOADING & SKELETON STATES
--------------------------------------------------------------------
Support:

- Skeleton loading.
- Shimmer foundation.
- Spinner.
- Progress indicator.
- Button loading.
- Image placeholder transition.

Shimmer must be disabled or simplified under reduced-motion or
performance constraints.

Loading animation must never continue indefinitely after a resolved
request.


19. SUCCESS / ERROR FEEDBACK
--------------------------------------------------------------------
Support:

Success:

- Checkmark transition.
- Toast.
- Inline confirmation.

Error:

- Subtle shake foundation.
- Error highlight.
- Toast.
- Inline state transition.

Error animation must not be excessive or disorienting.

Business status remains authoritative from the relevant module.


20. MODAL / DRAWER ANIMATIONS
--------------------------------------------------------------------
Support:

- Fade.
- Slide.
- Scale.
- Backdrop transition.

Requirements:

- Focus management.
- Keyboard support.
- Escape behavior.
- Screen-reader compatibility.
- Reduced-motion alternative.
- Mobile-safe interaction.


21. TOAST / NOTIFICATION ANIMATIONS
--------------------------------------------------------------------
Support:

- Enter.
- Exit.
- Progress/timeout indicator where appropriate.
- Stack/reorder behavior.

Toast animations must not hide critical error information.

Critical notifications may require persistent non-animated display.


22. SCROLL-BASED ANIMATIONS
--------------------------------------------------------------------
Optional features:

- Reveal on enter viewport.
- Fade-in.
- Slide-in.
- Scale-in.
- Staggered sections.
- Parallax foundation.

Safety rules:

1. No essential content may depend on scroll animation.
2. Content must remain accessible without animation.
3. Parallax must be disabled for reduced motion.
4. Heavy scroll listeners should use efficient browser APIs.
5. Avoid layout-triggering calculations on every scroll event.


23. STAGGER ANIMATIONS
--------------------------------------------------------------------
Support controlled stagger for:

- Product grids.
- Category grids.
- Navigation menus.
- Content sections.

Stagger must have:

- Maximum item count.
- Maximum total duration.
- Reduced-motion behavior.
- Mobile simplification.

Large catalogs must never produce hundreds of sequential animations.


24. GESTURE FOUNDATION
--------------------------------------------------------------------
Future-capable gesture support may include:

- Swipe.
- Drag.
- Pull.
- Horizontal carousel movement.
- Drawer swipe.

Gestures must:

- Be optional.
- Respect native scrolling.
- Support cancellation.
- Support keyboard alternatives.
- Support accessibility.
- Avoid accidental destructive actions.

Business actions must require appropriate confirmation where needed.


25. CAROUSEL MOTION
--------------------------------------------------------------------
Carousel animations may support:

- Slide.
- Fade.
- Crossfade.
- Drag/swipe.
- Auto-rotation.

Auto-rotation requirements:

- Pause on interaction.
- Pause when not visible where appropriate.
- Provide accessible controls.
- Respect reduced motion.
- Avoid rapidly changing essential content.


26. IMAGE TRANSITIONS
--------------------------------------------------------------------
Support:

- Fade between image variants.
- Progressive image reveal.
- Blur-up foundation.
- Placeholder-to-image transition.

Image transitions must not create layout shifts.

Width/height should be reserved before image loading.


27. REDUCED-MOTION ACCESSIBILITY
--------------------------------------------------------------------
This is mandatory.

The system must respect:

- prefers-reduced-motion.
- Store-level reduced-motion settings where applicable.
- User preferences.

When reduced motion is active:

- Disable non-essential motion.
- Remove parallax.
- Remove large transforms.
- Reduce duration.
- Simplify transitions.
- Preserve state-change feedback through static visual cues.

Reduced motion must never remove essential status information.


28. MOTION INTENSITY
--------------------------------------------------------------------
Support:

NONE
LOW
MEDIUM
HIGH

Intensity affects only non-essential animation.

It must not affect:

- Business rules.
- Order processing.
- Payment.
- Inventory.
- Security.
- Data validation.


29. DEVICE ADAPTATION
--------------------------------------------------------------------
The system may adapt animation based on:

- Device class.
- Reduced-motion preference.
- CPU/performance signals where reliably available.
- Network conditions where appropriate.
- Battery-saving context where available.
- Viewport size.

Never fingerprint users unnecessarily.

Default behavior should remain conservative.


30. PERFORMANCE BUDGETS
--------------------------------------------------------------------
Animations must avoid:

- Excessive JavaScript.
- Large runtime libraries when unnecessary.
- Forced synchronous layout.
- Excessive repaint.
- Excessive GPU memory usage.
- Large simultaneous animations.
- Long blocking transitions.

Prefer performant properties such as:

- transform.
- opacity.

Avoid animating layout-heavy properties unless necessary.


31. PERFORMANCE SAFETY GUARD
--------------------------------------------------------------------
The engine should support automatic safeguards:

- Disable heavy effects on constrained devices.
- Limit simultaneous animations.
- Limit stagger count.
- Limit parallax.
- Reduce blur.
- Reduce shadow intensity.
- Stop animations when off-screen.
- Cancel obsolete animations.

The system should fail toward simpler motion, not broken UI.


32. INTERACTION PRIORITY
--------------------------------------------------------------------
Animation priority levels:

P0 — Critical business feedback.
P1 — Important interaction feedback.
P2 — Navigation/continuity.
P3 — Decorative.

Under performance pressure:

P3 is removed first.
P2 is simplified.
P1 is retained where useful.
P0 remains as static/accessible feedback if animation is unavailable.

--------------------------------------------------------------------
Supported conceptual states:

IDLE
ENTERING
ACTIVE
HOVERED
PRESSED
LOADING
SUCCESS
ERROR
EXITING
DISABLED
CANCELLED

It only represents presentation state.


34. INTERRUPTIBILITY
--------------------------------------------------------------------
Animations must be interruptible.

Examples:

- User navigates away during transition.
- Product card state changes rapidly.
- Modal closes while opening.
- Loading resolves during skeleton animation.
- User changes theme while previewing.

The system must cancel or replace obsolete animation safely.


35. ANIMATION QUEUE
--------------------------------------------------------------------
Only animations that require sequencing should use a queue.

Rules:

- No unbounded queues.
- Maximum queue length.
- Cancellation.
- Deduplication.
- Priority.
- Timeout.

Critical UI interactions must not wait behind decorative animations.

DRAFT
→ PREVIEW
→ APPROVED
→ PUBLISHED
→ SCHEDULED
→ ROLLED_BACK
→ ARCHIVED

Rollback must restore a previously published configuration without
changing business data.

- Auditable.

41. SECURITY
--------------------------------------------------------------------
Animation configuration must never be able to:

- Execute arbitrary server-side code.
- Access secrets.
- Read another tenant's data.
- Modify business data.
- Bypass permissions.
- Inject malicious scripts.

Any custom animation configuration must be schema-based.

Custom JavaScript animation should not be enabled through ordinary
store configuration.


42. ACCESSIBILITY
--------------------------------------------------------------------
Requirements:

- Keyboard-compatible interactions.
- Visible focus.
- Reduced-motion support.
- No content hidden permanently by animation.
- No flashing content that can create accessibility hazards.
- No interaction that requires precise timing.
- Screen-reader state changes must be communicated independently.
- Animation must not trap focus.


43. FLASH / VISUAL SAFETY
--------------------------------------------------------------------
The system must prevent:

- Rapid flashing.
- Excessive strobing.
- High-frequency color changes.
- Rapid scale changes.

Decorative effects must remain within safe visual limits.


44. RTL / LTR MOTION
--------------------------------------------------------------------
Directional animations must respect text direction.

Examples:

LTR:
Drawer enters from left/right according to design.

RTL:
Directional relationships should be mirrored where appropriate.

The system should use logical directional semantics rather than
hard-coded assumptions.


45. MULTILINGUAL SUPPORT

RULE 01:
Module 18 is tenant-scoped for store-owned motion configuration.

RULE 02:
One core motion engine serves all packages.

RULE 03:
Animation profiles and motion tokens are configuration-driven.

RULE 04:
Published animation configurations are immutable.

RULE 05:
Animation is presentation logic, not business logic.

RULE 06:
Animation must never become the source of truth for orders,
payments, inventory, checkout, or customer data.

RULE 07:
Critical business operations must work without animation.

RULE 08:
Reduced-motion support is mandatory.

RULE 09:
Motion must degrade gracefully under performance constraints.

RULE 10:
Prefer transform and opacity for performant animation.

RULE 11:
Avoid animation that causes unnecessary layout/reflow.

RULE 12:
Decorative animation must never block critical interaction.

RULE 13:
Animations must be interruptible.

RULE 14:
Unbounded animation queues are prohibited.

RULE 15:
Large-scale simultaneous animations must be limited.

RULE 16:
Scroll effects must use efficient observation techniques and must
not hide essential content.

RULE 17:
Parallax must be disabled for reduced-motion users.

RULE 18:
Hover behavior must never be required for touch users.

RULE 19:
Directional animation must respect RTL/LTR semantics.

RULE 20:
Theme Module 17 selects/configures animation integration; Module 18
owns runtime motion behavior.

RULE 21:
Package entitlements control advanced animation capabilities.

RULE 22:
Custom JavaScript animation is not ordinary store configuration.

RULE 23:
Custom motion must use validated schemas.

RULE 24:
Preview must never modify production state.

RULE 25:
Rollback must preserve all business data.

RULE 26:
Animation configuration caches must always preserve tenant identity.

RULE 27:
All privileged motion configuration changes must be auditable.

RULE 28:
Animation events must not falsely imply successful business
operations.

RULE 29:
Performance and accessibility are mandatory product requirements.

RULE 30:
Module 18 must integrate through explicit contracts, APIs, events,
schemas, and ownership boundaries.
