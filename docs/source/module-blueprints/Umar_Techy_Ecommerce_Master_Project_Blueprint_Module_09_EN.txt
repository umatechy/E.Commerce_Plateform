UMAR TECHY
E-COMMERCE PLATFORM
MASTER PROJECT BLUEPRINT

MODULE 09 — ORDER MANAGEMENT
Version: 1.0
Status: Planning / Blueprint

============================================================
1. MODULE PURPOSE
============================================================

This module defines the centralized Order Management architecture
for the Umar Techy multi-tenant E-Commerce Platform.

The Order Management system is the authoritative business
workflow connecting:

- Storefront
- Customers
- Cart
- Checkout
- Inventory
- Payments
- Shipping
- Notifications
- Returns
- Refunds
- Reports
- Analytics
- Billing integrations
- POS
- External integrations

The module defines order creation, validation, lifecycle,
fulfillment, cancellation, returns, refunds, order history,
order communication, administrative workflows, APIs, events,
security, auditability, and future extensibility.

============================================================
2. CORE ORDER PRINCIPLE
============================================================

ONE CORE ORDER ENGINE
+
TENANT-SCOPED ORDERS
+
IMMUTABLE FINANCIAL/HISTORICAL SNAPSHOTS
+
EXPLICIT ORDER STATE MACHINE
+
INTEGRATION EVENTS

must serve all stores.

Basic, Business, and Premium stores use the same Order Engine.

Package differences are enforced through Module 04.

============================================================
3. TENANT ISOLATION
============================================================

Every order belongs to exactly one Store/Tenant.

Store A must never be able to access:

- Store B orders
- Store B customers
- Store B addresses
- Store B payment details
- Store B shipping details
- Store B order notes
- Store B refunds
- Store B fulfillment data
- Store B order exports

Tenant context must be enforced at API, database, cache, search,
background job, event, notification, and reporting layers.

============================================================
4. ORDER ENTITY
============================================================

An Order represents a confirmed or attempted commercial
transaction.

Potential core fields:

- Order ID
- Store/Tenant ID
- Order Number
- Customer ID
- Order Status
- Payment Status
- Fulfillment Status
- Currency
- Subtotal
- Discount Total
- Shipping Total
- Tax Total
- Grand Total
- Customer Snapshot
- Billing Address Snapshot
- Shipping Address Snapshot
- Notes
- Source
- Created At
- Updated At
- Completed At
- Cancelled At

Exact schema will be defined in the Database Blueprint.

============================================================
5. INTERNAL ORDER ID VS ORDER NUMBER
============================================================

The system should distinguish:

INTERNAL ORDER ID:
Stable technical identifier.

ORDER NUMBER:
Customer-facing identifier.

Example:

Internal:
UUID/ID

Customer-facing:
UT-2026-000123

Order number should be unique within the appropriate store or
platform scope according to the final design.

6. ORDER SOURCES

Orders may originate from:

- Web Storefront
- PWA
- Mobile App
- Admin Panel
- POS
- API
- Marketplace Integration
- Social Commerce
- Future Sales Channels

Every order should record its source.

7. ORDER TYPES

The architecture may support:

============================================================
8. GUEST ORDERS
============================================================

Guest customers may place orders if the store allows guest
checkout.

Guest order data should retain the information required for:

- Fulfillment
- Customer communication
- Returns
- Refunds
- Legal/business records

Guest orders should not require a permanent customer account.

============================================================
9. CUSTOMER ORDERS
============================================================

Registered customers should have orders linked to their
store-scoped customer identity.

Customers may view only their own permitted orders.

============================================================
10. ORDER SNAPSHOT PRINCIPLE
============================================================

Orders must preserve historical information.

At order creation, capture appropriate snapshots of:

- Product Name
- SKU
- Variant
- Unit Price
- Discount
- Tax
- Quantity
- Product image/reference where appropriate
- Customer details
- Shipping address
- Billing address
- Applied promotion details

Later catalog changes must not rewrite historical order
information.

============================================================
11. ORDER LINE ITEM
============================================================

Each order contains one or more line items.

Potential fields:

- Order Line ID
- Product ID reference
- Variant ID reference
- Product Name Snapshot
- SKU Snapshot
- Variant Snapshot
- Quantity
- Unit Price
- Discount
- Tax
- Line Total
- Fulfillment Status

Internal product references may be retained while snapshots
protect historical integrity.

============================================================
12. ORDER TOTALS
============================================================

Order totals should be calculated from authoritative server-side
data.

Conceptual:

Subtotal
- Discounts
+ Tax
+ Shipping
+ Additional Charges
= Grand Total

The final calculation engine must be centralized.

============================================================
13. MONEY REPRESENTATION
============================================================

Financial values must use a safe decimal/money representation.

Do not use binary floating-point arithmetic for authoritative
financial calculations.

Each order should store the relevant currency.

============================================================
14. ORDER CURRENCY
============================================================

The order must preserve the currency used at the time of
purchase.

Future store currency changes must not alter historical order
currency.

============================================================

16. ORDER STATUS VS PAYMENT STATUS

ORDER STATUS:
Commercial/fulfillment lifecycle.

Order:
CANCELLED

REFUND_PENDING

============================================================
20. SERVER-SIDE VALIDATION
============================================================

Before creating an order, validate:

- Store is active
- Customer/guest data valid
- Products exist
- Variants valid
- Products purchasable
- Prices current
- Discounts valid
- Stock available
- Shipping available
- Payment method available
- Currency valid
- Package/store restrictions
- Fraud/abuse controls where enabled

============================================================
21. CLIENT DATA TRUST
============================================================

Never trust client-submitted:

- Product Price
- Discount Amount
- Tax Amount
- Shipping Amount
- Order Total
- Payment Status
- Inventory Availability
- Store ID

The server must derive authoritative values.

============================================================
22. ORDER NUMBER GENERATION
============================================================

Order number generation should be:

- Unique
- Collision-safe
- Tenant-aware where configured
- Human-readable
- Stable
- Non-guessable enough to avoid exposing sensitive sequencing
  where necessary

The internal ID remains the authoritative technical key.

============================================================
23. ORDER DEDUPLICATION
============================================================

Duplicate order creation must be prevented.

Potential causes:

- Double click
- Browser retry
- Network retry
- Payment gateway callback retry
- POS retry
- Offline sync retry

Use idempotency keys and server-side duplicate detection.

============================================================
24. IDEMPOTENCY
============================================================

Order creation APIs should support idempotency.

Example:

Client sends:
Idempotency-Key = ABC123

Request times out.

Client retries with:
Idempotency-Key = ABC123

The server must not create a second order.

============================================================
25. PAYMENT-ORDER COORDINATION
============================================================

Order and payment workflows must be coordinated carefully.

Possible online payment flow:

Checkout
→ Create Pending Order / Payment Intent
→ Payment Gateway
→ Gateway Confirmation
→ Verify Payment Server-to-Server
→ Mark Payment Paid
→ Confirm Order
→ Commit Inventory

Exact implementation belongs to Module 12.

============================================================
26. COD ORDER FLOW
============================================================

For Cash on Delivery:

Checkout
→ Validate
→ Confirm Order
→ Reserve/Commit Inventory according to store policy
→ Fulfillment
→ Delivery
→ Payment Collection
→ Mark Paid

The exact inventory and payment transition must be explicit.

============================================================
27. BANK TRANSFER FLOW
============================================================

Possible workflow:

Order Created
→ Payment Pending
→ Customer Receives Bank Details
→ Customer Uploads/Provides Proof if enabled
→ Admin Verification
→ Payment Confirmed
→ Order Confirmed

Payment proof must be securely stored and permission-controlled.

============================================================
28. PAYMENT FAILURE
============================================================

If payment fails:

- Order should not become falsely paid.
- Inventory reservation should be released according to policy.
- Customer should receive actionable information.
- Payment failure should be recorded.
- Retry may create a new payment attempt without duplicating
  the order unnecessarily.

============================================================
29. PAYMENT CALLBACK SECURITY
============================================================

Gateway callbacks/webhooks must be:

- Authenticated
- Signature verified
- Idempotent
- Tenant-aware
- Validated
- Logged
- Replay-resistant where possible

Never trust a client-side payment success page as proof of
payment.

============================================================
30. ORDER TIMELINE

Each order should have a timeline.

Order Created

Packed
Shipped

- System
- Timestamp
- Status

- Reference

distinguished.

31. ORDER NOTES

- Customer Note

39. ORDER ITEM MODIFICATION
============================================================

Changing confirmed order items may affect:

- Inventory
- Pricing
- Tax
- Discounts
- Payment
- Shipping

Therefore, direct mutation should be restricted.

Use explicit adjustment workflows.

40. ORDER ADJUSTMENTS
============================================================

- Change quantity
- Price adjustment

- Discount adjustment

- Reason
- Actor
- Previous value
- New value
- Financial impact
- Inventory impact

============================================================
41. ORDER CANCELLATION
============================================================

Cancellation may be requested by:

- Customer
- Store staff
- System
- Payment failure
- Fraud/abuse workflow

Cancellation rules should depend on order state.

============================================================
42. CANCELLATION RULES
============================================================

Example:

PENDING:
Can cancel.

CONFIRMED:
May cancel according to policy.

PROCESSING:
May require staff approval.

SHIPPED:
Normally requires return workflow.

DELIVERED:
Use return/cancellation policy.

The exact rules must be configurable.

============================================================
43. CANCELLATION REASON
============================================================

Cancellation should capture:

- Reason Code
- Optional Note
- Actor
- Timestamp

Examples:

- Customer Request
- Out of Stock
- Payment Failed
- Address Issue
- Fraud Review
- Store Cancellation

============================================================
44. INVENTORY ON CANCELLATION
============================================================

If inventory was reserved or committed, cancellation must
trigger the appropriate inventory operation.

Example:

Reserved
→ Release

Committed but not shipped
→ Return to available stock where appropriate

Exact behavior belongs to Inventory and Fulfillment logic.

============================================================
45. RETURN REQUEST
============================================================

Customers may request returns where the store allows them.

Return request may contain:

- Order
- Order Items
- Quantity
- Reason
- Description
- Images
- Requested Resolution

Possible resolutions:

- Refund
- Replacement
- Exchange
- Store Credit

============================================================
46. RETURN STATES

============================================================
47. PARTIAL RETURNS
============================================================

A customer may return only some items.

Example:

Order:
5 products

2 products

The system must support item-level quantities and return
status.

============================================================
48. RETURN INSPECTION
============================================================

Returned physical products may require inspection.

Possible result:

Resalable
→ Inventory In

Damaged
→ Damaged Stock

Rejected
→ Return to Customer / Other workflow

Inventory changes must be auditable.

============================================================
49. REFUNDS
============================================================

Refunds must be represented separately from orders.

Potential refund states:

PENDING
PROCESSING
SUCCEEDED
FAILED
CANCELLED

A refund may be:

- Full
- Partial

============================================================
50. REFUND CALCULATION
============================================================

Refund amount must account for:

- Returned quantity
- Item price
- Discounts
- Tax
- Shipping policy
- Restocking fees where legally/business appropriate
- Previous refunds

The system must prevent refunding more than the eligible
amount.

============================================================
51. REFUND IDEMPOTENCY
============================================================

Refund operations must be idempotent.

Gateway retry must not create duplicate refunds.

Use provider transaction IDs and internal idempotency keys.

============================================================
52. STORE CREDIT FOUNDATION
============================================================

Future support may include store credit.

Store credit should be:

- Tenant-scoped
- Auditable
- Non-negative unless explicitly supported
- Expiry-aware where applicable
- Protected from unauthorized manipulation

============================================================
53. EXCHANGES
============================================================

Future exchange workflow may support:

Returned Item
→ Replacement Item

The system should preserve:

- Original order reference
- Return
- Replacement
- Inventory movements
- Financial adjustments

============================================================
54. REPLACEMENT ORDERS
============================================================

A replacement order may be created from a return.

It should retain a relationship to the original order without
destroying historical data.

============================================================
55. FULFILLMENT

Fulfillment represents the process of preparing and delivering

Potential steps:

- Allocate Warehouse

- Deliver

============================================================
75. AUDIT LOGGING
============================================================

- Order cancellation

76. ORDER SEARCH INDEX

- User/customer context

82. FRAUD / ABUSE FOUNDATION
============================================================

The architecture should reserve support for order risk controls.

Signals may include:

- Excessive failed payments
- Repeated COD cancellations
- Unusual order velocity
- Repeated address patterns
- Suspicious API behavior

Risk systems must be carefully scoped and auditable.

============================================================
83. COD RISK FOUNDATION
============================================================

For COD-heavy stores, future controls may include:

- COD order limits
- Customer order history
- Verification
- Phone confirmation
- WhatsApp confirmation
- Manual approval

============================================================
84. ORDER LIMITS
============================================================

Package entitlements may limit:

- Monthly orders
- Order history retention
- Staff order access
- Advanced fulfillment
- Returns
- Refund automation
- API order volume
- Webhooks

============================================================
85. ORDER NUMBERING AND PRIVACY
============================================================

Customer-facing order numbers should avoid unnecessary exposure
of total platform order volume.

Stores may use tenant-scoped numbering.

Internal IDs should never be treated as customer-facing order
numbers by default.

============================================================
86. ORDER DATA RETENTION
============================================================

Order records may need long-term retention for:

- Business records
- Customer service
- Refunds
- Returns
- Accounting
- Legal requirements
- Analytics

Retention must be defined separately from active order
visibility.

============================================================
87. ORDER DELETION
============================================================

Orders should generally not be hard-deleted merely because a
customer or product is removed.

Historical financial/business integrity must be preserved.

Use:

- Retention
- Anonymization where appropriate
- Restricted archival

according to legal/business requirements.

============================================================
88. CUSTOMER DATA ANONYMIZATION

============================================================
107. FINAL ARCHITECTURAL RULES
============================================================

1. One Core Order Engine.
2. Every order must be tenant-scoped.
3. Customer-facing order numbers are distinct from internal IDs.
4. Historical order snapshots must be preserved.
5. Order, payment, and fulfillment statuses must remain distinct.
6. Client-side financial values are never authoritative.
7. Order creation must be server-validated.
8. Idempotency is mandatory for retry-sensitive order operations.
9. Payment callbacks must be verified and idempotent.
10. Inventory coordination must prevent overselling.
11. Confirmed orders must not be casually mutated.
12. Financial adjustments require controlled workflows.
13. Cancellation rules must be state-aware.
14. Returns must support partial quantities.
15. Refunds must support partial refunds.
16. Refund totals must never exceed eligible amounts.
17. Fulfillment must support future multi-warehouse allocation.
18. POS and offline orders must use the same Core Order Engine.
19. External order IDs must be supported.
20. Webhooks must be signed, retryable, and auditable.
21. Order events should use reliable delivery mechanisms.
22. Private order data must never be publicly cached.
23. Order exports must be tenant-scoped and audited.
24. Historical order integrity must survive product/customer changes.
25. All critical order workflows must support reconciliation.
