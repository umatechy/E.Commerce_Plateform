MODULE 04 — SUBSCRIPTION, PACKAGES & FEATURE ENTITLEMENTS
Version: 1.0
Status: Planning / Blueprint

============================================================
1. MODULE PURPOSE
============================================================

This module defines the commercial package, subscription,
feature entitlement, usage-limit, trial, upgrade, downgrade,
renewal, suspension, and access-control framework for the
Umar Techy E-Commerce Platform.

The platform will use ONE Core E-Commerce Platform.

Basic, Business, and Premium are commercial packages built on
top of the same Core Platform.

A customer must never receive a separately developed software
system simply because they selected a different package.

Instead:

ONE CORE PLATFORM
+
PACKAGE ENTITLEMENTS
+
FEATURE FLAGS / ACCESS RULES
+
USAGE LIMITS
+
OPTIONAL ADD-ONS

will determine the capabilities available to each Store/Tenant.

This module must work closely with:

- Module 02 — Authentication, Users, Roles & Permissions
- Module 03 — Multi-Tenant & Store Management
- Module 29 — Billing, Invoices & Renewals

============================================================
2. CORE COMMERCIAL PRINCIPLE
============================================================

The platform should be developed once and monetized through
multiple commercial packages.

Example:

Store A → BASIC
Store B → BUSINESS
Store C → PREMIUM

All three stores use the same application.

The package determines:

- Available Features
- Available Modules
- Usage Limits
- Resource Limits
- Support Level
- Theme Access
- Animation Access
- Integration Access
- AI Access
- API Access
- Storage
- Order Capacity
- Staff Capacity

============================================================
4. PACKAGE DESIGN PRINCIPLE
============================================================

Packages should not be implemented as unrelated code paths.

Bad approach:

IF BASIC → separate code
IF BUSINESS → separate code
IF PREMIUM → separate code

Preferred approach:

Core Feature
+
Entitlement Check
+
Usage Limit
+
Package Access
+
Optional Add-On

This keeps the platform maintainable and scalable.

Example:

monthly_orders = 1000

F. ACCESS LEVEL ENTITLEMENT

Example:

G. AI ENTITLEMENT

============================================================
10. HARD LIMIT VS SOFT LIMIT
============================================================

The platform should distinguish between:

HARD LIMIT

The action is blocked when the limit is reached.

Example:

Maximum products = 500

Product 501 cannot be activated.

SOFT LIMIT

The customer receives warnings and may continue temporarily
under defined conditions.

Example:

Storage approaching package limit.

The exact behavior must be defined per resource.

============================================================

Example:

  ↓
BUSINESS
  ↓
PREMIUM

- Store ID
- Tenant ID
- Products
- Orders
- Customers
- Inventory
- Domain
- Storefront
- Store branding

============================================================
21. UPGRADE
============================================================

Upgrade should provide a controlled transition.

Example:

Basic → Business

Expected behavior:

- Existing data remains intact.
- New features become available.
- New limits become active.
- New resources become available according to plan.
- Billing changes are recorded.
- Customer receives confirmation.

If upgrade is immediate, the exact billing proration rules
will be handled by Module 29.

============================================================
22. DOWNGRADE
============================================================

Downgrade is more complex because existing usage may exceed
the new package limits.

Example:

Business:
Products = 2,000

Basic:
Maximum Products = 500

The system should NOT silently delete 1,500 products.

Instead it should:

- Detect over-limit resources
- Notify customer
- Prevent new usage beyond the limit
- Provide resolution guidance
- Preserve existing data according to policy

Possible resolution options:

- Remove excess data
- Archive excess data
- Upgrade again
- Purchase add-on capacity

The final policy will be defined later.

============================================================
28. FEATURE FLAGS VS ENTITLEMENTS
============================================================

Feature Flags and Commercial Entitlements must remain distinct.

FEATURE FLAG

Controls software rollout or technical availability.

ENTITLEMENT

Controls whether a customer is commercially authorized to use
a feature.

Example:

Feature technically available = YES

Store entitlement = NO

Result:

Feature remains unavailable to that store.

This separation is important for safe development and staged
rollouts.

29. PACKAGE ACCESS EVALUATION

3. Store active?

============================================================
36. PACKAGE EXPIRY BEHAVIOR
============================================================

When subscription access expires:

1. Subscription state changes.
2. Entitlements are recalculated.
3. Store enters the appropriate lifecycle state.
4. Customer receives notification.
5. Grace period rules apply where applicable.
6. Restricted features are handled safely.
7. Store may eventually be suspended.

The system must avoid immediate destructive behavior.

============================================================
37. DATA PRESERVATION DURING EXPIRY
============================================================

Subscription expiry must not automatically delete customer
business data.

Data such as:

- Products
- Orders
- Customers
- Inventory
- Reports
- Store configuration

should be preserved according to retention policies.

The store may become restricted, but data preservation remains
separate from access state.

============================================================
38. REACTIVATION
============================================================

When a suspended or expired store becomes active again:

- Subscription is validated.
- Entitlements are recalculated.
- Store access is restored.
- Usage limits are re-evaluated.
- Services resume according to package.

Historical data must remain intact.

56. ENTITLEMENT CACHING
============================================================

Entitlements may be cached for performance, but cache
invalidation must be reliable.

When a package changes:

- Entitlement cache must refresh.
- API access must reflect the new state.
- Background jobs must use the new state.
- UI must refresh appropriately.

Security-sensitive access decisions must not depend on stale
cache data beyond defined safety boundaries.

============================================================
57. FAIL-SAFE BEHAVIOR
============================================================

When entitlement information cannot be safely determined,
sensitive protected operations should fail closed.

The system should not assume:

"Unable to check entitlement = allow"

Instead:

"Unable to safely verify access = deny or controlled fallback"

depending on the operation.

============================================================
62. SECURITY NON-NEGOTIABLES
============================================================

- Never trust package or entitlement values from the client.
- Never enforce package access only in the UI.
- Never allow API bypass of package restrictions.
- Never allow one tenant to modify another tenant's package.
- Never allow one tenant to consume another tenant's quota.
- Never expose internal commercial configuration unnecessarily.
- Never silently delete customer data during downgrade.
- Never allow expired access through stale authorization state.
- Never log payment secrets or credentials.
- Never allow unauthorized entitlement overrides.
- Never allow support staff to grant arbitrary premium access.
- Every privileged entitlement override must be auditable.
