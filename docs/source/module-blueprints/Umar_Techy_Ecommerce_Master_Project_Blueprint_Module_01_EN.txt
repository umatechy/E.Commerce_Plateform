============================================================
1. MODULE PURPOSE
============================================================

This module defines the complete high-level structure of the
Umar Techy E-Commerce Platform.

The purpose is to establish the foundation before development
starts, so the core architecture does not need to be repeatedly
rebuilt for individual customers.

The platform will follow a Multi-Tenant SaaS model.

The Core E-Commerce Platform will be developed once. Each new
customer will receive a new Store/Tenant instance within the
existing platform instead of requiring a completely new
application to be developed.

This document is the initial Master Project Blueprint.
It will later be expanded and connected with the complete
Project Bible, URS, SRS, Database Blueprint, API Blueprint,
Architecture Blueprint, Design System, Security Blueprint,
Testing Strategy, and Deployment Strategy.

============================================================
2. CORE BUSINESS MODEL
============================================================

Umar Techy will operate the E-Commerce Platform as a
Multi-Tenant SaaS product.

Core concept:

Umar Techy E-Commerce Platform
    |
    +-- Store / Tenant 001
    +-- Store / Tenant 002
    +-- Store / Tenant 003
    +-- Store / Tenant 004
    +-- Store / Tenant 005
    +-- ...

All stores will use the same Core Software Platform.

Each store will have isolated business data and its own
configuration.

Each store may have its own:

- Store Identity
- Owner Account
- Products
- Categories
- Brands
- Customers
- Orders
- Inventory
- Branding
- Theme
- Animation Settings
- Domain
- Payment Settings
- Shipping Settings
- Business Settings
- Subscription / Package
- Reports
- Integrations

The platform must enforce strict tenant isolation.

14. Store Configuration
15. Store Activation

self-service onboarding.

============================================================
6. THREE CORE COMMERCIAL PACKAGES
============================================================

Package 01 — BASIC

Designed for small and entry-level e-commerce businesses.

Package 02 — BUSINESS

Designed for established and growing businesses requiring
advanced operational capabilities.

Package 03 — PREMIUM

Designed for advanced businesses, high-volume stores, brands,
and customers requiring advanced features and integrations.

Critical architectural rule:

These are NOT three separate software systems.

There will be ONE Core Platform.

Package-based entitlements will determine which modules,
features, limits, integrations, and capabilities are available
to each store.

============================================================
10. DOMAIN MANAGEMENT FRAMEWORK
============================================================

The platform will support two primary domain models.

A. Customer-Owned Domain

The customer already owns a domain and connects it to the store.

B. Umar Techy Managed Domain

Umar Techy purchases and/or manages the domain as an additional
service.

The system must associate each domain with the correct Store/Tenant.

Domain management should support:

- Domain Verification
- DNS Guidance / Configuration
- Domain Status
- SSL Status
- Renewal Tracking
- Primary Domain
- Custom Domain Mapping
- Platform Subdomain
- Domain Ownership Records

Ownership and renewal responsibilities must be clearly defined
for every domain.

============================================================
11. HOSTING & INFRASTRUCTURE MODEL
============================================================

Two primary deployment models will be supported.

A. Umar Techy Managed Hosting

Umar Techy manages:

- Server Infrastructure
- Backend
- Database
- Storage
- SSL
- Backups
- Monitoring
- Infrastructure Security
- Basic Operations

This is the preferred SaaS model.

B. Customer-Provided Hosting

Where required, the platform may be deployed to a
customer-provided infrastructure.

This model may have separate:

- Setup Fees
- Deployment Fees
- Maintenance Fees
- Support Fees
- Infrastructure Requirements

The architecture should keep the application portable enough
to support both models where technically practical.

23. SECURITY PRINCIPLE
============================================================

Because the platform is Multi-Tenant, tenant isolation is a
non-negotiable requirement.

A store must never be able to access another store's data
through:

- Web Interface
- API
- Database Queries
- Files
- Media
- Reports
- Search
- Background Jobs
- Exports
- Integrations

Core security areas:

- Tenant Isolation
- Authentication
- Authorization
- Role-Based Access Control
- Input Validation
- API Security
- Secret Management
- Audit Logging
- File / Media Security
- Rate Limiting
- Session Security
- Backup Security
- Data Encryption where appropriate
- Secure Configuration
- Security Monitoring

A dedicated Security Blueprint will define implementation
requirements.

24. CORE ARCHITECTURE PRINCIPLE
============================================================

Golden Rule:

ONE CORE PLATFORM
+
MANY STORES / TENANTS

26. CLAUDE DEVELOPMENT WORKFLOW PRINCIPLE
============================================================

Claude must work from the approved project documentation.

Before implementing any module, Claude should:

1. Read the relevant Project Bible and Blueprint documents.
2. Inspect the existing codebase and current implementation.
3. Identify existing reusable components.
4. Avoid rebuilding existing functionality unnecessarily.
5. Implement the requested scope.
6. Run relevant tests.
7. Fix discovered issues.
8. Run the tests again.
9. Review security and tenant isolation impact.
10. Update documentation where required.
11. Provide a clear completion report.
12. Commit changes only when the defined workflow permits it.

The objective is to minimize later manual development.
