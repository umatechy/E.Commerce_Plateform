UMAR TECHY
E-COMMERCE PLATFORM
MASTER PROJECT BLUEPRINT

MODULE 06 — PRODUCT & CATALOG MANAGEMENT
Version: 1.0
Status: Planning / Blueprint

============================================================
1. MODULE PURPOSE
============================================================

This module defines the centralized product and catalog
management architecture for the Umar Techy multi-tenant
E-Commerce Platform.

The catalog system must allow every Store/Tenant to manage its
own products and catalog data while using the same Core
E-Commerce Platform.

The module covers:

- Products
- Product lifecycle
- Product types
- Product information
- Product media
- SKUs
- Variants
- Options
- Pricing
- Sale pricing
- Product status
- Product visibility
- Catalog organization
- Collections
- Tags
- Product relationships
- Digital/physical product foundations
- Bulk operations
- Import/export
- Product search indexing
- Catalog validation
- Tenant isolation
- Auditability
- Package limits
- API foundations
- Future extensibility

Detailed Category, Brand and Attribute architecture will be
expanded in Module 07, while inventory execution will be
expanded in Module 08.

============================================================
2. CORE CATALOG PRINCIPLE
============================================================

ONE CORE CATALOG ENGINE
+
TENANT-SCOPED DATA
+
CONFIGURABLE PRODUCT TYPES
+
PACKAGE ENTITLEMENTS

must serve all stores.

There must not be separate catalog codebases for Basic,
Business, or Premium stores.

Package differences are enforced through Module 04
entitlements and usage limits.

============================================================
3. TENANT ISOLATION
============================================================

Every catalog record must belong to exactly one appropriate
Store/Tenant scope unless it is explicitly a global platform
record.

Tenant-owned catalog data includes:

- Products
- Product Variants
- SKUs
- Prices
- Media
- Tags
- Collections
- Product Metadata
- Product Relationships
- Catalog settings

A Store A request must never be able to read, modify, delete,
or index Store B catalog data.

============================================================
4. CATALOG DATA OWNERSHIP
============================================================

The catalog system must clearly distinguish:

GLOBAL PLATFORM DATA:

- System-supported product types
- Global feature definitions
- Platform defaults
- Approved media rules
- Global safety configuration

TENANT DATA:

- Products
- Product descriptions
- SKUs
- Prices
- Variants
- Media
- Categories
- Collections
- Tags
- Product visibility
- Catalog settings

The final database blueprint must make ownership explicit.

============================================================
5. PRODUCT ENTITY
============================================================

A Product represents a sellable or displayable catalog item.

Core fields may include:

- Product ID
- Store/Tenant ID
- Product Type
- Name
- Slug
- SKU where applicable
- Short Description
- Full Description
- Status
- Visibility
- Brand ID where applicable
- Primary Category
- Published At
- Created At
- Updated At
- Archived At
- SEO Metadata
- Catalog Metadata

The exact database schema will be defined separately.

============================================================
6. PRODUCT TYPES
============================================================

The architecture should support multiple product types.

Initial types may include:

1. Simple Physical Product
2. Variable Physical Product
3. Digital Product
4. Service Product
5. Bundle Product

Future types may include:

- Subscription Product
- Gift Card
- Donation
- Booking Product
- Custom Product
- External/Affiliate Product

The system should avoid hard-coded assumptions that every
product is a single physical item.

============================================================
7. SIMPLE PRODUCT
============================================================

A simple product has one primary sellable configuration.

Example:

Product:
Cotton T-Shirt

SKU:
TSH-001

No customer-selectable variant is required.

Simple products may still support:

- Pricing
- Stock
- Media
- Categories
- Tags
- Discounts
- SEO
- Shipping configuration

============================================================
8. VARIABLE PRODUCT
============================================================

A variable product contains multiple sellable variants.

Example:

T-Shirt

Color:
Black
White

Size:
S
M
L
XL

Each valid combination may have its own:

- SKU
- Price
- Sale Price
- Stock
- Image
- Weight
- Dimensions
- Barcode
- Availability

Variant behavior must remain compatible with inventory and
checkout modules.

============================================================
9. PRODUCT VARIANT
============================================================

A Product Variant is an independently sellable configuration
of a parent product.

A variant may have:

- Variant ID
- Product ID
- SKU
- Barcode
- Price
- Sale Price
- Cost Price where permitted
- Weight
- Dimensions
- Media
- Inventory reference
- Status
- Metadata

Variant identifiers must be unique within the appropriate
tenant scope.

============================================================
10. VARIANT GENERATION
============================================================

The system may generate variant combinations from option values.

Example:

Color:
Black, White

Size:
S, M, L

Possible combinations:

Black/S
Black/M
Black/L
White/S
White/M
White/L

The system must prevent duplicate or invalid combinations.

For large variant sets, generation must be controlled to prevent
resource abuse.

============================================================
11. VARIANT LIMITS
============================================================

Package entitlements may define limits for:

- Variants per product
- Total variants
- Options per product
- Attribute values
- Product complexity

The exact commercial limits should be finalized in Module 04
after catalog design is complete.

============================================================
12. PRODUCT NAME
============================================================

Product names must support:

- Required value
- Tenant scope
- Validation
- Length limits
- Safe rendering
- Search indexing

Duplicate names may be allowed unless the store configuration
requires uniqueness.

============================================================
13. PRODUCT SLUG
============================================================

Every public product should have a safe URL slug.

Requirements:

- Tenant-scoped uniqueness
- URL-safe
- Stable where possible
- Normalized
- Reserved-word protection
- Duplicate handling

Example:

/products/premium-cotton-shirt

Slug changes should support redirect handling where appropriate.

============================================================
14. PRODUCT DESCRIPTION
============================================================

Products should support:

- Short Description
- Full Description
- Specifications
- Usage Information
- Materials
- Care Instructions
- Additional Details

Content must be safely sanitized before public rendering.

============================================================
15. RICH PRODUCT CONTENT
============================================================

Where supported, product descriptions may contain:

- Headings
- Lists
- Tables
- Images
- Links
- Basic formatting
- Embedded approved content

Arbitrary unsafe scripts must never be allowed.

============================================================
16. PRODUCT MEDIA
============================================================

Products may contain:

- Main Image
- Gallery Images
- Variant Images
- Product Videos
- Documents where supported

Media should support:

- Alt Text
- Sort Order
- Caption
- Type
- Visibility
- Variant Association

============================================================
17. MEDIA RULES
============================================================

Media upload rules should enforce:

- Allowed file types
- File size limits
- Image dimensions
- Malware/security checks where applicable
- Safe filenames
- Storage quotas
- Tenant isolation

Original files and generated derivatives should be managed
through the platform media architecture.

============================================================
18. IMAGE DERIVATIVES
============================================================

The platform should support generated image sizes such as:

- Thumbnail
- Small
- Medium
- Large
- Original

The storefront should request the most appropriate size.

This reduces bandwidth and improves performance.

============================================================
19. ALT TEXT
============================================================

Product images should support meaningful alt text.

The system may provide automatic suggestions, but store
administrators should be able to edit them.

Accessibility and SEO should both be considered.

============================================================
20. SKU
============================================================

SKU stands for Stock Keeping Unit.

SKU requirements:

- Tenant-scoped uniqueness
- Safe characters
- Configurable format
- Optional for non-inventory products where appropriate
- Required for products/variants where inventory workflows
  require it

The system must prevent accidental duplicate SKUs within a
store.

============================================================
21. BARCODE
============================================================

Products or variants may support barcode identifiers.

Potential barcode types may include:

- EAN
- UPC
- ISBN
- Store-defined barcode

Barcode uniqueness should be configurable and validated.

============================================================
22. PRICING
============================================================

The catalog must support authoritative base pricing.

Potential fields:

- Regular Price
- Sale Price
- Cost Price
- Compare-at Price
- Minimum Price
- Maximum Price for ranges
- Currency
- Tax configuration reference

Final order pricing is recalculated server-side during cart and
checkout.

============================================================
23. SALE PRICE
============================================================

Sale pricing may be:

- Fixed amount
- Scheduled
- Time limited
- Store-wide
- Product-specific
- Variant-specific

The catalog should expose effective pricing to the storefront.

============================================================
24. PRICE VALIDATION
============================================================

Client-submitted prices must never be trusted.

The server must derive price from:

- Product
- Variant
- Current catalog price
- Active promotion
- Customer eligibility
- Store currency
- Applicable tax
- Shipping rules

This protects against price manipulation.

============================================================
25. COST PRICE
============================================================

Cost price may be stored for store administration and
profitability calculations.

Cost price must never be exposed to customers.

Access must be restricted through permissions.

============================================================
26. CURRENCY
============================================================

Each store has its own currency configuration.

Product pricing must respect the store currency rules.

Multi-currency architecture may be reserved for future
expansion.

If multi-currency is introduced later, the catalog must support
currency-specific pricing without breaking existing orders.

============================================================
27. PRODUCT STATUS
============================================================

Products should support lifecycle states such as:

DRAFT
ACTIVE
SCHEDULED
HIDDEN
ARCHIVED

Optional future states:

DISCONTINUED
PENDING_REVIEW
REJECTED

Only appropriate active products should appear publicly.

============================================================
28. PRODUCT VISIBILITY
============================================================

Visibility should be independently configurable.

Potential values:

- Public
- Catalog Only
- Search Only
- Hidden
- Private
- Scheduled

The final visibility model should work with:

- Storefront
- Search
- Categories
- Collections
- Recommendations
- Sitemap
- APIs

============================================================
29. PUBLISHING
============================================================

Product publishing should support:

- Save Draft
- Validate
- Preview
- Publish
- Unpublish
- Schedule
- Archive

Publishing must validate required information.

============================================================
30. PRODUCT SCHEDULING
============================================================

Stores may schedule:

- Product publication
- Product unpublication
- Sale pricing
- Collection membership
- Promotional visibility

Scheduling must use the store's configured timezone.

============================================================
31. PRODUCT ARCHIVING
============================================================

Archived products should normally:

- Stop appearing in normal storefront catalog
- Stop appearing in search
- Stop appearing in recommendations
- Remain available for historical orders
- Preserve historical references

Deleting historical product records should not break old orders.

============================================================
32. HISTORICAL ORDER INTEGRITY
============================================================

Orders must retain a historical snapshot of relevant product
information.

If a product changes later, old orders should not unexpectedly
change.

Historical order data may include:

- Product Name
- SKU
- Variant
- Unit Price
- Discount
- Tax
- Product image/reference where appropriate

Exact order snapshot design belongs to Module 09.

33. CATALOG ORGANIZATION

Products may be organized through:

- Categories
- Brands

- Manual

41. SERVICE PRODUCTS

Physical products may support:

43. PRODUCT OPTIONS
============================================================

Options represent customer-selectable product choices.

Examples:

- Color
- Size
- Capacity
- Material

Detailed attribute architecture is defined in Module 07.

============================================================
44. REQUIRED PRODUCT VALIDATION
============================================================

Before publishing a product, validate:

- Product Name
- Product Type
- Slug
- Price where required
- SKU where required
- Required media where configured
- Required category
- Required variant data
- Required digital asset for digital products
- Required shipping data for physical products
- Store package entitlement

Validation should produce actionable errors.

============================================================
45. DRAFT VALIDATION
============================================================

Draft products may be incomplete.

Publishing should enforce stricter validation than saving a
draft.

This allows stores to build products progressively.

============================================================
46. BULK PRODUCT OPERATIONS
============================================================

The platform should support bulk operations.

Potential operations:

- Publish
- Unpublish
- Archive
- Delete where safe
- Change Category
- Change Collection
- Update Price
- Update Sale Price
- Update Tags
- Update Visibility
- Update Stock reference
- Export

Bulk operations must be permission-controlled.

============================================================
47. BULK OPERATION SAFETY
============================================================

Bulk operations must:

- Show affected record count
- Require confirmation for destructive actions
- Respect package limits
- Respect permissions
- Create audit records
- Handle partial failures safely
- Avoid cross-tenant execution

Large jobs should use background processing.

============================================================
48. PRODUCT IMPORT
============================================================

The platform should support product import.

Potential formats:

- CSV
- Spreadsheet-compatible files
- Future API import

Import may include:

- Product data
- SKUs
- Prices
- Categories
- Tags
- Variants
- Attributes

============================================================
49. IMPORT VALIDATION
============================================================

Import should use a staged process:

Upload
  ↓
Parse
  ↓
Validate
  ↓
Preview
  ↓
Confirm
  ↓
Process
  ↓
Report

Invalid rows should produce clear errors.

One bad row should not necessarily corrupt the entire import.

============================================================
50. IMPORT IDEMPOTENCY
============================================================

Import should support safe reprocessing where possible.

Potential matching keys:

- Product ID
- SKU
- External ID

The system must prevent accidental duplicate product creation
during repeated imports.

============================================================
51. PRODUCT EXPORT
============================================================

Stores may export catalog data according to permissions.

Exports may include:

- Products
- Variants
- Prices
- SKUs
- Categories
- Collections
- Tags
- Attributes
- Media references

Exports must be tenant-scoped.

52. PACKAGE LIMITS

Potential limits:

- Total Products
- Active Products
- Variants
- Categories
- Collections
- Media Storage
- Product Imports
- Product Exports
- API catalog operations

Limits must be configurable rather than hard-coded.

============================================================
53. LIMIT ENFORCEMENT
============================================================

Limits should be checked during:

- Manual product creation
- Bulk creation
- Import
- API creation
- Variant generation
- Media upload

The system should provide clear upgrade messaging when a limit

Indexable fields may include:

- Product Name
- SKU
- Description
- Tags
- Brand
- Category
- Attributes

55. SEARCH INDEX CONSISTENCY
============================================================

When catalog data changes:

Product Created
Product Updated
Product Published
Product Unpublished
Product Archived
Product Deleted

the search index should be updated reliably.

Background jobs may be used.

Failures should be retryable and observable.

============================================================
56. CACHE INVALIDATION

Catalog updates may invalidate:

- Product cache
- Category cache
- Collection cache
- Search cache
- Homepage product sections
- Recommendation cache

Cache keys must contain tenant/store context.

58. AUDIT LOGGING
============================================================

Important catalog changes should be auditable.

Examples:

- Product created

- SKU changed

59. PRODUCT VERSIONING
============================================================

The architecture should reserve versioning for important product
content.

Potentially version:

- Description
- Pricing configuration
- SEO
- Media ordering
- Visibility
- Product configuration

Versioning is especially useful for rollback and audit.

============================================================
60. PRODUCT DUPLICATION
============================================================

Store administrators may duplicate products.

Duplication should:

- Create a new Product ID
- Generate a safe new slug
- Prevent duplicate SKU
- Copy permitted content
- Copy media references safely
- Preserve tenant scope
- Reset fields that must be unique

Example:

Original:
Premium Shirt

Duplicate:
Premium Shirt Copy

The final UX may allow immediate editing of the duplicated
product.

============================================================
61. PRODUCT DELETION
============================================================

Deletion must be carefully controlled.

A product referenced by historical orders should not be
hard-deleted if doing so would break historical integrity.

Possible approach:

- Soft delete
- Archive
- Retain historical snapshot

Destructive deletion should require elevated permissions where
appropriate.

============================================================
62. PRODUCT RESTORE
============================================================

Where soft deletion is used, authorized users may restore
products.

Restore must revalidate:

- SKU
- Slug
- Category
- Store status
- Package limits
- Product configuration

- Save draft state

If multiple staff members edit the same product, the system

Possible strategies:

- Updated-at conflict detection
- Version number
- Optimistic concurrency
- Draft locking where required

Silent overwriting should be avoided.

69. PRODUCT URL REDIRECTS

Availability may depend on:

- Cross-tenant access

- Unauthorized product modification
- Price manipulation
- SKU duplication
- Unsafe HTML
- Malicious uploads
- Unauthorized exports
- Bulk operation abuse
- API abuse

Media handling must ensure:

- File type validation

============================================================

The architecture may support a catalog readiness indicator.

Example categories:

- Product Completeness
- Media Completeness
- Pricing Completeness
- SEO Completeness
- Variant Completeness
- Shipping Completeness

This should be advisory unless explicitly configured as a
publication requirement.

============================================================
91. PRODUCT COPY AND CONTENT SAFETY
============================================================

Product content must be sanitized.

The system should protect against:

- Script injection
- Dangerous HTML
- Unsafe URLs
- Embedded malicious content

Store administrators should not be allowed to bypass platform
security controls through product descriptions.

============================================================
92. PRODUCT DUPLICATE DETECTION
============================================================

The system may detect likely duplicate products using:

- SKU
- Barcode
- External ID
- Similar name
- Optional AI similarity

Duplicate detection should provide warnings rather than silently
merging products.

============================================================
93. CATALOG MERCHANDISING
============================================================

The architecture should support merchandising controls such as:

- Featured
- Sort priority
- Manual product ordering
- Collection priority
- Category priority
- Promotional placement

These controls must remain tenant-specific.

============================================================
94. MANUAL PRODUCT SORTING
============================================================

Stores may manually arrange products within supported sections.

The ordering model should use a scalable ordering strategy
rather than requiring large-scale database rewrites.

============================================================
95. PRODUCT RELATIONSHIP VALIDATION
============================================================

Product relationships must validate:

- Source product exists
- Target product exists
- Same tenant
- Valid relationship type
- No prohibited circular relationship
- Target product visibility where required

============================================================
96. CATALOG SNAPSHOTS
============================================================

The architecture should reserve catalog snapshots for:

- Backup
- Restore
- Migration
- Audit
- Versioning
- Bulk changes

Snapshots must preserve tenant boundaries.

============================================================
97. CATALOG MIGRATION
============================================================

When the platform schema evolves, migrations must preserve:

- Product IDs
- Variant IDs
- SKUs
- Historical references
- Media references
- Tenant ownership

Migration scripts must not perform unsafe destructive changes
without explicit controlled procedures.

============================================================
98. STORE CLONING FOUNDATION
============================================================

Module 03 reserves future store cloning.

Catalog architecture should support cloning selected catalog
configuration into another store only through an explicit,
authorized process.

Never expose source-store data to the destination store
unintentionally.

============================================================
99. CATALOG API RESPONSE RULES
============================================================

Public storefront APIs should return only required public data.

Never expose:

- Cost Price
- Internal Notes
- Supplier Data
- Internal Audit Data
- Private Media
- Security Metadata
- Internal IDs where not needed

Admin APIs may return additional fields according to permissions.

============================================================
100. PUBLIC CATALOG CACHE
============================================================

Public product data may be cached aggressively where safe.

Cache invalidation must occur after relevant updates.

Cache keys must include:

- Store/Tenant
- Product
- Locale where applicable
- Currency where applicable
- Channel where applicable

============================================================
101. LOCALE-AWARE CATALOG
============================================================

Future multilingual product content should support:

- Product Name Translation
- Description Translation
- SEO Translation
- Category Translation
- Attribute Translation

The architecture should avoid assuming one language forever.

============================================================
102. RTL CATALOG SUPPORT
============================================================

Product content must render correctly in RTL languages.

The data model should store content independently of visual
direction.

The storefront decides presentation direction based on locale.

============================================================
103. CURRENCY-AWARE CATALOG
============================================================

The catalog should separate:

- Base price data
- Store currency
- Display formatting

Future multi-currency support should not require redesigning
the core product entity.

============================================================
104. PRODUCT STATUS TRANSITIONS
============================================================

Allowed transitions should be controlled.

Example:

DRAFT
  → ACTIVE
  → SCHEDULED
  → ARCHIVED

SCHEDULED
  → ACTIVE
  → DRAFT
  → ARCHIVED

ACTIVE
  → HIDDEN
  → ARCHIVED

ARCHIVED
  → RESTORED / DRAFT where allowed

Invalid transitions must be rejected.

============================================================
105. PRODUCT EVENTUAL CONSISTENCY
============================================================

Some catalog operations may be eventually consistent.

Examples:

- Search indexing
- Analytics
- Recommendations
- Cache invalidation
- CDN derivative generation

Critical purchase operations must not rely on stale catalog
information.

116. FINAL ARCHITECTURAL RULES
============================================================

1. One Core Catalog Engine.
2. All catalog records must have explicit tenant ownership.
3. Basic, Business, and Premium use the same catalog engine.
4. Package restrictions must be entitlement-driven.
5. Product IDs must remain stable.
6. Historical orders must not depend on mutable product data.
7. Client-side prices are never authoritative.
8. SKU uniqueness must be tenant-scoped.
9. Product slugs must be tenant-scoped.
10. Variants must remain tied to the parent product.
11. Product status must control public visibility.
12. Draft products must not leak publicly.
13. Archived products must preserve historical references.
14. Media must be tenant-isolated.
15. Search indexes must be tenant-isolated.
16. Cache keys must be tenant-aware.
17. Bulk operations must be permission-controlled.
18. Imports must validate before committing data.
19. Exports must be tenant-scoped.
20. Product content must be sanitized.
21. Cost price must never be exposed publicly.
22. Critical purchase values must be recalculated server-side.
23. Catalog events must provide extension points.
24. AI must not silently overwrite authoritative data.
25. Catalog design must remain extensible for future channels.
