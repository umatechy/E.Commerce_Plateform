1. MODULE PURPOSE
--------------------------------------------------------------------
Module 19 provides the Core Domain Management Engine for the Umar
Techy Multi-Tenant E-Commerce Platform.

The module manages the relationship between stores/tenants and their
public web domains, including:

- Platform subdomains.
- Customer-owned custom domains.
- Umar Techy-managed domains.
- Domain verification.
- DNS verification foundations.
- Domain attachment.
- Primary domain selection.
- Domain aliases.
- HTTPS/SSL readiness.
- Domain status.
- Domain redirects.
- Domain lifecycle.
- Domain health.
- Tenant-safe routing.
- Domain migration.
- Domain removal.
- Domain ownership metadata.
- Future automated domain purchasing/renewal integration.

Core principle:

ONE CORE MULTI-TENANT PLATFORM
        +
DOMAIN RESOLUTION LAYER
        +
TENANT-SCOPED DOMAIN RECORDS
        +
VERIFICATION / SSL STATE
        +
SAFE PUBLIC ROUTING

No domain configuration may expose one tenant's storefront,
content, files, sessions, or data to another tenant.


2. PRIMARY OBJECTIVES
--------------------------------------------------------------------
The module shall:

1. Resolve incoming domains to the correct tenant/store.
2. Support platform-generated subdomains.
3. Support customer-owned custom domains.
4. Support Umar Techy-managed domains.
5. Support multiple domains per store where entitled.
6. Provide primary-domain selection.
7. Provide domain verification workflows.
8. Provide DNS verification foundations.
9. Provide HTTPS/SSL lifecycle foundations.
10. Support domain aliases and redirects.
11. Prevent domain collisions.
12. Prevent host-header attacks.
13. Prevent cross-tenant routing.
14. Support domain migration.
15. Support domain removal.
16. Provide domain health/status.
17. Integrate with storefront, SEO, hosting, and infrastructure.
18. Preserve tenant identity during domain changes.
19. Support future automated registrar integration.
20. Provide comprehensive security and testing.


3. ARCHITECTURAL POSITION
--------------------------------------------------------------------
Module 19 owns:

- Domain records.
- Domain normalization.
- Domain verification.
- Domain attachment.
- Primary-domain selection.
- Domain aliases.
- Domain routing metadata.
- Domain lifecycle.
- Domain redirect configuration.
- Domain health metadata.
- SSL status metadata.
- DNS verification state.
- Domain migration state.
- Registrar integration foundation.

Module 19 does NOT own:

- Store identity/lifecycle — Module 03.
- Subscription/package entitlement — Module 04.
- Hosting infrastructure — Module 20.
- SEO rules — Module 16.
- Theme — Module 17.
- Animation — Module 18.
- Payment processing — Module 12.
- Email delivery — Module 21.

Those modules remain authoritative for their respective domains.


4. DOMAIN TYPES
--------------------------------------------------------------------
Supported domain types:

PLATFORM_SUBDOMAIN
CUSTOMER_OWNED_DOMAIN
UMAR_TECHY_MANAGED_DOMAIN
DOMAIN_ALIAS
FUTURE_MARKETPLACE_DOMAIN

Examples conceptually:

store-name.platform-domain.tld
www.customer-domain.tld

The actual platform domain must be environment-specific and must not
be hard-coded into business logic.


5. DOMAIN OWNERSHIP MODEL
--------------------------------------------------------------------
Every custom domain must have an ownership classification:

CUSTOMER_OWNED
UMAR_TECHY_MANAGED
UNCLASSIFIED_PENDING_VERIFICATION

Ownership metadata may include:

- Owner type.
- Owner reference.
- Registration provider reference.
- Registrar reference.
- Expiry date where available.
- Renewal status.
- Transfer status.

Domain ownership information must never be treated as proof of
ownership until verification succeeds.


6. DOMAIN NORMALIZATION
--------------------------------------------------------------------
Before storage or comparison, domains must be normalized.

Normalization should include:

- Lowercase hostname.
- Unicode/punycode handling.
- Removal of accidental trailing dot where appropriate.
- Port removal.
- Scheme removal for hostname comparison.
- Safe whitespace handling.
- IDN validation.
- Label validation.

The system must distinguish:

Hostname
from
Full URL.

Only valid hostnames may be registered.


7. DOMAIN VALIDATION
--------------------------------------------------------------------
Validate:

- Domain syntax.
- Label length.
- Total hostname length.
- Allowed characters.
- IDN/punycode rules.
- Reserved platform domains.
- Restricted subdomains.
- Unsupported public suffix patterns.
- Internal/private hostnames.
- Localhost and loopback addresses where applicable.

Reject dangerous or invalid values.


8. PLATFORM SUBDOMAIN SYSTEM
--------------------------------------------------------------------
Each store may receive a platform subdomain.

Requirements:

- Globally unique.
- Stable while store exists.
- Safe slug.
- Tenant-linked.
- Available before custom domain configuration.
- Suitable as fallback domain.

Subdomain changes, if allowed, must use redirect/alias handling and
preserve the old route where appropriate.


9. CUSTOM DOMAIN ATTACHMENT
--------------------------------------------------------------------
Workflow:

Enter Domain
→ Normalize
→ Validate
→ Check Availability
→ Create Pending Domain
→ Generate Verification Instructions
→ Verify Ownership
→ Validate DNS
→ Provision/Validate SSL
→ Attach to Store
→ Optional Primary Selection
→ Activate

A domain must never become an active public tenant route before
verification and required infrastructure checks succeed.


10. DOMAIN AVAILABILITY / COLLISION
--------------------------------------------------------------------
Before attachment, verify:

- Domain is not attached to another tenant.
- Domain is not reserved.
- Domain is not a platform infrastructure domain.
- Domain is not blocked.
- Domain is not already pending for another store.
- Domain does not create an unsafe wildcard collision.

Concurrency controls are required so two tenants cannot claim the
same domain simultaneously.


11. PRIMARY DOMAIN
--------------------------------------------------------------------
Each store may have one primary public domain.

Primary domain rules:

- Must be verified.
- Must be active.
- Must have required HTTPS readiness.
- Must belong to the same tenant.
- Must be unique per store.

Changing the primary domain must be transactional.

The previous primary domain may become an alias/redirect according to
store policy.


12. DOMAIN ALIASES
--------------------------------------------------------------------
A store may have aliases such as:

- www version.
- Non-www version.
- Legacy domain.
- Previous platform subdomain.
- Alternate verified domain.

Alias behavior may be:

- Redirect to primary.
- Serve same storefront where technically appropriate.

SEO-sensitive domains should normally redirect to the canonical
primary domain rather than create duplicate indexable storefronts.


13. WWW / NON-WWW POLICY
--------------------------------------------------------------------
The platform should support:

- Primary apex domain.
- Primary www hostname.

The system should define a deterministic canonical policy.

Example:

https://example.com
or
https://www.example.com

Only one should normally be the canonical public hostname.

Redirect behavior must avoid loops.


14. DNS VERIFICATION
--------------------------------------------------------------------
Support verification methods such as:

- TXT record.
- CNAME record.
- File-based verification foundation.
- Provider API verification where supported.

Verification records should include:

- Domain.
- Method.
- Token/challenge.
- Created timestamp.
- Expiry.
- Status.
- Attempt history.

Tokens must be unpredictable and tenant-scoped.


15. DNS CONFIGURATION GUIDANCE
--------------------------------------------------------------------
The admin UI should provide clear instructions for:

- A record.
- CNAME.
- TXT verification.
- www configuration.
- Apex configuration.
- Nameserver/provider-specific configuration where applicable.

The platform must not assume every registrar supports identical

DNS instructions must be environment-aware.

21. TENANT ROUTING
--------------------------------------------------------------------
Incoming request routing:

Request Host
→ Normalize Host
→ Resolve Domain
→ Resolve Store/Tenant
→ Validate Store State
→ Resolve Locale/Theme/Content
→ Continue to Storefront

The domain resolver must execute before tenant-owned storefront
data is accessed.


22. HOST HEADER SECURITY
--------------------------------------------------------------------
The platform must not trust arbitrary Host headers.

Controls:

- Allowlisted domain records.
- Verified domain status.
- Environment-aware host validation.
- Proxy-aware trusted-host configuration.
- Reject unknown hosts.
- Prevent host-header injection.
- Prevent password-reset poisoning.
- Prevent absolute-URL poisoning.

Never construct tenant URLs solely from untrusted Host input.


23. CROSS-TENANT PROTECTION
--------------------------------------------------------------------
The following must remain isolated:

- Domains.
- Sessions.
- Cookies.
- Storefront cache.
- SEO metadata.
- Themes.
- Content.
- Media.
- API context.
- Webhooks.
- Redirects.
- Analytics identifiers.

A domain mapped to Store A must never resolve to Store B.


24. COOKIE & SESSION DOMAIN POLICY
--------------------------------------------------------------------
Domain routing must integrate with authentication safely.

Requirements:

- Store-specific cookie strategy.
- Avoid overly broad cookie domains.
- Secure flag in production.
- HttpOnly where appropriate.
- SameSite policy.
- Tenant-aware session isolation.

Custom-domain storefront sessions must not leak to another domain.


25. CANONICAL URL INTEGRATION
--------------------------------------------------------------------
Module 16 consumes the active primary domain from Module 19.

When primary domain changes:

- Canonical URLs update according to SEO policy.
- Sitemap URLs update.
- Social URLs update.
- Redirects may be created.
- Cache must be invalidated.
- Old domain handling must be preserved according to configuration.

Module 19 owns domain identity; Module 16 owns SEO canonical rules.

- Confirm cache cleanup.

Removal should use a safe multi-step workflow.

44. DATA INTEGRITY RULES
--------------------------------------------------------------------
1. A normalized domain can belong to only one active tenant mapping.
2. A store can have only one primary domain.
3. A primary domain must be verified and active.
4. Unverified domains cannot become production-active.
5. Domain state transitions must be valid.
6. Domain removal must not silently delete tenant data.
7. Domain migration must preserve Store ID/Tenant ID.
8. Redirect destinations must be validated.
9. Unknown hosts must not resolve to arbitrary tenants.
10. Domain verification tokens must be unique and unpredictable.
11. Domain records must be auditable.
12. Registrar credentials must never be exposed in logs.
13. DNS/SSL state must be distinguishable from ownership verification.
14. Cross-tenant domain references must be rejected.


45. CACHE & ROUTING PERFORMANCE
--------------------------------------------------------------------
Domain resolution is a high-frequency operation.

Use:

- In-memory caching.
- Distributed caching.
- Edge/CDN lookup where appropriate.
- Efficient indexed domain lookup.

Cache keys must use normalized hostname.

Cache invalidation is required after:

- Domain activation.
- Primary-domain change.
- Domain removal.
- Domain suspension.
- Domain migration.

Never cache tenant resolution in a way that can survive an incorrect
mapping after domain reassignment.


46. RATE LIMITING
--------------------------------------------------------------------
Rate-limit:

- Domain verification attempts.
- DNS checks.
- Health checks.
- Domain creation.
- Domain deletion.
- Registrar API calls.
- Transfer operations.

Prevent automated abuse and excessive provider requests.

Every active custom domain must belong to exactly one tenant.

RULE 03:
One store may have multiple domains only when permitted by
entitlements.

RULE 04:
A store may have only one primary public domain at a time.

RULE 05:
A domain must be verified before production activation.

RULE 06:
Domain ownership verification and DNS configuration are distinct
states.

RULE 07:
SSL state and domain ownership state are distinct states.

RULE 08:
Unknown Host headers must never resolve to an arbitrary tenant.

RULE 09:
Host headers are untrusted input.

RULE 10:
Tenant resolution must occur before tenant-owned storefront data is
loaded.

RULE 11:
Domain mapping must never permit cross-tenant data access.

RULE 12:
Primary-domain changes must preserve Store ID and Tenant ID.

RULE 13:
Domain migration must not clone or recreate the store.

RULE 14:
Old domains should be redirected only according to explicit safe
policy.

RULE 15:
Open redirects are prohibited.

RULE 16:
Domain verification tokens must be unpredictable and short-lived
where applicable.

RULE 17:
Registrar credentials and transfer secrets must never appear in
