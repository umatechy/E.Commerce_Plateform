1. MODULE PURPOSE
--------------------------------------------------------------------
Module 21 provides the Core Notifications and Communication Delivery
Engine for the Umar Techy Multi-Tenant E-Commerce Platform.

The module is responsible for technically delivering messages across
supported communication channels while preserving tenant isolation,
customer preferences, consent requirements, reliability, delivery
tracking, provider abstraction, templates, retries, and auditability.

Supported channels:

- Email.
- SMS.
- WhatsApp.
- Push notifications.
- In-app notifications.
- Storefront notifications.
- Future Telegram/Messenger channels.
- Future voice/call channels where legally and technically supported.

Core principle:

ONE CORE COMMUNICATION ENGINE
        +
MULTIPLE CHANNEL ADAPTERS
        +
TENANT-SCOPED CONFIGURATION
        +
CONSENT/PREFERENCE ENFORCEMENT
        +
RELIABLE ASYNCHRONOUS DELIVERY
        +
DELIVERY TRACKING

Module 15 decides marketing audience, campaign intent, and
automation logic.

Module 21 decides how an authorized message is technically delivered.


2. PRIMARY OBJECTIVES
--------------------------------------------------------------------
The module shall:

1. Provide a centralized communication delivery architecture.
2. Support multiple communication channels.
3. Provide provider adapter abstraction.
4. Support transactional notifications.
5. Support marketing message delivery from Module 15.
6. Enforce customer communication preferences.
7. Enforce consent requirements.
8. Support unsubscribe/suppression enforcement.
9. Provide tenant-specific provider configurations.
10. Provide reusable message templates.
11. Support localization.
12. Support queue-based asynchronous delivery.
13. Support retries and backoff.
14. Support idempotent delivery.
15. Track message and delivery status.
16. Process provider webhooks.
17. Support provider failover foundations.
18. Protect against abuse and messaging fraud.
19. Provide cost/usage tracking.
20. Support package-based communication limits.
21. Provide observability and auditability.
22. Provide comprehensive testing.

→ Determine Message Type
→ Resolve Recipient
→ Resolve Tenant
→ Check Eligibility
→ Check Consent/Preference
→ Resolve Template
→ Resolve Locale
→ Render Message
→ Select Channel/Provider
→ Queue Delivery
→ Send
→ Receive Provider Result
→ Update Delivery State
→ Emit Event
→ Record Analytics/Audit

eligibility checks.

30. IDEMPOTENCY
--------------------------------------------------------------------

- Event retries.
- Queue retries.
- Worker restarts.
- Provider timeouts.
- Webhook duplication.

A timeout after provider submission must not automatically create a
duplicate message without reconciliation.
