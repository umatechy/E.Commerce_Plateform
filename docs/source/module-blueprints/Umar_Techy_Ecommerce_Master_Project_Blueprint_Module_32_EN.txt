DOCUMENT PURPOSE
------------------------------------------------------------
This module defines the complete security, audit, privacy,
compliance, governance, and security-operations foundation for the
Umar Techy Core Multi-Tenant E-Commerce SaaS.

Security is a platform-wide responsibility. This module establishes
the controls that protect:
- Umar Techy platform infrastructure
- Tenant/store data
- Customer data
- Administrator accounts
- Developer applications
- API credentials
- Payment integrations
- Billing records
- Inventory and order integrity
- Files and media
- Backups
- Logs and audit records
- Webhooks and integrations
- AI capabilities
- Marketplace applications
- Internal services
- Super Admin operations

This module does not replace the security requirements defined in
individual modules. It provides the centralized security framework
that all modules MUST follow.

DOCUMENT LANGUAGE
------------------------------------------------------------
All technical specifications in this module are intentionally
written in English.

============================================================
1. MODULE OBJECTIVES
============================================================

1.1 Establish defense-in-depth security across the entire platform.
1.2 Protect all tenants from cross-tenant access and data leakage.
1.3 Protect user accounts, credentials, sessions, tokens, and secrets.
1.4 Protect business-critical resources from unauthorized modification.
1.5 Establish immutable or tamper-resistant auditability.
1.6 Provide privacy-by-design controls.
1.7 Establish secure development and deployment practices.
1.8 Provide security monitoring, alerting, incident response, and
    recovery procedures.
1.9 Establish compliance-ready foundations without claiming legal
    certification automatically.
1.10 Protect APIs, webhooks, integrations, files, backups, and queues.
1.11 Establish security policies for Super Admin and internal access.
1.12 Provide security testing and continuous regression controls.
1.13 Support future regional, regulatory, enterprise, and compliance
    requirements.

2. SECURITY PRINCIPLES
============================================================

2.1 Security by design.
2.2 Secure by default.
2.3 Least privilege.
2.4 Zero trust between security boundaries.
2.5 Explicit authorization.
2.6 Tenant isolation by default.
2.7 Defense in depth.
2.8 Fail closed for security-sensitive operations.
2.9 Minimize collected data.
2.10 Minimize exposed data.
2.11 Minimize credential lifetime.
2.12 Never trust client-controlled authorization data.
2.13 Never trust external provider data without validation.
2.14 Never expose secrets in logs.
2.15 Never commit secrets to source control.
2.16 Never bypass security to simplify development.
2.17 Security controls must be testable.
2.18 Security events must be observable.
2.19 Sensitive actions must be auditable.
2.20 Security incidents must have defined response procedures.

============================================================
6. IDENTITY SECURITY
============================================================

6.1 All authenticated identities MUST be uniquely identifiable.
6.2 Authentication MUST be separated from authorization.
6.3 User identity MUST never be inferred from client-controlled fields.
6.4 Account status MUST be evaluated on every sensitive operation.
6.5 Suspended/deactivated users MUST lose access according to policy.
6.6 Deleted identities MUST follow documented retention requirements.
6.7 Service identities MUST be separate from human identities.

============================================================
7. PASSWORD SECURITY
============================================================

7.1 Passwords MUST be stored using a modern adaptive password hash.
7.2 Recommended algorithms include:
- Argon2id
- bcrypt where legacy compatibility requires it

7.3 Plaintext passwords MUST never be stored.
7.4 Passwords MUST never appear in logs.
7.5 Password reset tokens MUST:
- Be random
- Be single-use
- Expire
- Be invalidated after successful reset

7.6 Password reset MUST not reveal whether an account exists through
    overly specific public responses.
7.7 Password policy SHOULD support configurable minimum strength.
7.8 Password reuse controls may be implemented for higher-risk roles.

============================================================
8. MULTI-FACTOR AUTHENTICATION
============================================================

8.1 MFA SHOULD be supported for:
- Super Admin
- Tenant owners
- High-privilege administrators
- Developer organizations
- Enterprise integrations

8.2 Supported methods may include:
- TOTP
- Passkeys/WebAuthn
- Security keys
- Approved recovery methods

8.3 MFA recovery MUST be strongly protected.
8.4 Recovery codes MUST be single-use and securely stored.
8.5 MFA enrollment and removal MUST be audited.
8.6 Disabling MFA for privileged accounts SHOULD require additional
    verification.

============================================================
9. SESSION SECURITY
============================================================

9.1 Sessions MUST have defined expiration.
9.2 Refresh tokens MUST be protected.
9.3 Refresh token rotation SHOULD be used.
9.4 Session revocation MUST be supported.
9.5 Password changes SHOULD invalidate appropriate active sessions.
9.6 Suspicious session activity may trigger reauthentication.
9.7 Browser cookies MUST use:
- Secure
- HttpOnly where appropriate
- SameSite appropriate to the application

9.8 Session identifiers MUST be unpredictable.
9.9 Session fixation MUST be prevented.
9.10 Sensitive operations may require step-up authentication.

============================================================
10. AUTHORIZATION SECURITY
============================================================

10.1 Authorization MUST be enforced server-side.
10.2 Roles MUST not be treated as the only authorization layer.
10.3 Authorization SHOULD combine:
- User
- Role
- Permission
- Scope
- Tenant
- Resource ownership
- Package entitlement
- Application status
- Operation sensitivity

10.4 Object-level authorization is mandatory.
10.5 Field-level authorization MUST be used for sensitive data.
10.6 Write permissions MUST be allowlisted.
10.7 Mass assignment MUST be prevented.
10.8 Authorization failures MUST not disclose sensitive resource data.

============================================================
11. TENANT ISOLATION SECURITY
============================================================

11.1 Tenant isolation is a critical security boundary.
11.2 Every tenant-scoped query MUST enforce tenant context.
11.3 Every tenant-scoped resource MUST have ownership validation.
11.4 Tenant ID supplied by a client MUST never be trusted as sufficient.
11.5 Cross-tenant object access MUST fail.
11.6 Cross-tenant update MUST fail.
11.7 Cross-tenant delete MUST fail.
11.8 Cross-tenant export MUST fail.
11.9 Cross-tenant file access MUST fail.
11.10 Cross-tenant search MUST fail.
11.11 Cross-tenant cache retrieval MUST fail.
11.12 Cross-tenant webhook access MUST fail.
11.13 Cross-tenant analytics MUST fail.

11.14 Tenant isolation MUST be tested at:
- API
- Service
- Repository
- Database
- Cache
- Search
- Storage
- Queue
- Export
- Analytics
- Logs
- Webhooks

============================================================
12. OBJECT-LEVEL AUTHORIZATION
============================================================

12.1 Every resource access MUST validate resource ownership/scope.
12.2 Sequential or predictable IDs MUST not be treated as secret.
12.3 UUIDs do not replace authorization.
12.4 Resource existence MUST be concealed where appropriate.
12.5 Nested resources MUST validate every parent boundary.

============================================================

13.1 Follow Module 31.
13.2 Enforce HTTPS.
13.3 Enforce authentication where required.
13.4 Enforce authorization.
13.5 Enforce rate limits.
13.6 Validate request schemas.
13.7 Limit request size.
13.8 Protect against injection.
13.9 Protect against SSRF.

13.11 Protect against replay.

============================================================
14. API CREDENTIAL SECURITY
============================================================

14.1 API keys MUST be securely generated.
14.2 API secrets MUST not be stored in plaintext.
14.3 Secret display SHOULD be one-time where possible.
14.4 Credentials MUST support rotation.
14.5 Credentials MUST support revocation.
14.6 Credential usage MUST be auditable.
14.7 Credentials MUST be scoped.
14.8 Credentials MUST be tenant-bound where applicable.
14.9 Dormant credentials MAY expire according to policy.
14.10 Credentials must never be placed in client-side source code
     when they are intended to be secret.

============================================================
15. OAUTH SECURITY
============================================================

15.1 Use approved OAuth 2.0 flows.
15.2 Public clients MUST use PKCE.
15.3 Redirect URIs MUST be exact/allowlisted.
15.4 Authorization state MUST be protected.
15.5 Tokens MUST have appropriate expiry.
15.6 Refresh tokens MUST be protected and rotated where appropriate.
15.7 Scope escalation MUST require explicit authorization.
15.8 OAuth consent MUST identify the application and requested access.
15.9 Revoked installations MUST lose access.
15.10 OAuth secrets MUST never appear in logs.

============================================================
16. WEB SECURITY
============================================================

16.1 Prevent XSS.
16.2 Prevent CSRF where cookie authentication is used.
16.3 Prevent clickjacking.
16.4 Use appropriate Content Security Policy.
16.5 Use secure security headers.
16.6 Validate redirects.
16.7 Sanitize user-generated HTML.
16.8 Never render untrusted content as executable code.
16.9 Avoid inline executable scripts where practical.
16.10 Protect admin routes from public exposure.

============================================================
17. CORS SECURITY
============================================================

17.1 Use explicit origin allowlists.
17.2 Do not use wildcard origins for sensitive authenticated APIs.
17.3 Credentials-enabled CORS requires explicit origins.
17.4 Review allowed origins when domains change.
17.5 Remove stale origins.

============================================================
18. INPUT VALIDATION
============================================================

18.1 Validate every external input.
18.2 Use typed request schemas.
18.3 Validate:
- Type
- Length
- Format
- Range
- Enumeration
- Encoding
- Ownership
- Business constraints

18.4 Reject unexpected fields for security-sensitive requests.
18.5 Normalize input where required.
18.6 Validate file uploads independently.
18.7 Never rely only on frontend validation.

============================================================
19. INJECTION PROTECTION
============================================================

Protect against:
- SQL injection
- NoSQL injection where applicable
- Command injection
- Template injection
- LDAP injection where applicable
- Header injection
- Log injection
- HTML injection
- Script injection

19.1 Use parameterized database access.
19.2 Avoid shell execution from user-controlled input.
19.3 Encode output according to context.
19.4 Validate dynamic query fields against allowlists.

============================================================
20. SSRF PROTECTION
============================================================

20.1 Any feature that fetches a URL MUST validate destination.
20.2 Block private/internal network destinations unless explicitly
     required.
20.3 Block cloud metadata endpoints.
20.4 Restrict protocols.
20.5 Limit redirects.
20.6 Resolve and validate destination safely.
20.7 Apply network egress controls where practical.

============================================================
21. FILE AND MEDIA SECURITY
============================================================

21.1 Validate file type.
21.2 Validate actual MIME/content where possible.
21.3 Limit file size.
21.4 Generate safe storage names.
21.5 Never use user filename as a filesystem path.
21.6 Scan uploaded files where practical.
21.7 Store private files outside public web roots where possible.
21.8 Use short-lived signed URLs.
21.9 Enforce tenant/resource ownership.
21.10 Prevent executable uploads.
21.11 Image processing MUST protect against decompression bombs and
     malformed media where relevant.

============================================================
22. DATABASE SECURITY
============================================================

22.1 Database credentials MUST be stored in secure configuration.
22.2 Application users MUST receive least-privilege DB permissions.
22.3 Production databases MUST not be publicly exposed unnecessarily.
22.4 Database connections MUST use encryption where supported.
22.5 Sensitive data MUST have appropriate protection at rest.
22.6 Destructive administrative operations MUST be restricted.
22.7 Database migrations MUST be reviewed.
22.8 Backup access MUST be restricted.
22.9 Production database credentials MUST never be used in development.
22.10 Database activity should be monitored for critical operations.
