MASTER PROJECT BLUEPRINT

MODULE 08 — INVENTORY & STOCK MANAGEMENT
Version: 1.0
Status: Planning / Blueprint

============================================================
1. MODULE PURPOSE
============================================================

This module defines the centralized inventory and stock
management architecture for the Umar Techy multi-tenant
E-Commerce Platform.

The inventory system must support stores of different sizes,
from small sellers with one stock location to larger stores
with multiple warehouses, purchasing workflows, reservations,
adjustments, transfers, and future POS synchronization.

The module covers:

- Inventory
- Stock quantities
- Stock movements
- Warehouses
- Stock locations
- Stock reservations
- Available stock
- Incoming stock
- Outgoing stock
- Low-stock management
- Stock adjustments
- Stock transfers
- Inventory history
- Purchase receiving foundation
- Inventory valuation foundation
- Product/variant inventory
- Multi-warehouse support
- POS synchronization foundation
- Offline/sync readiness
- API
- Events
- Audit
- Package limits
- Security
- Performance
- Reporting foundations

============================================================
2. CORE INVENTORY PRINCIPLE
============================================================

ONE CORE INVENTORY ENGINE
+
TENANT-SCOPED STOCK
+
PRODUCT / VARIANT INTEGRATION
+
WAREHOUSE-READY ARCHITECTURE
+
ORDER RESERVATION
+
AUDITABLE STOCK MOVEMENTS

must serve every store.

Basic, Business, and Premium stores use the same inventory
engine.

Package differences are enforced through Module 04.

============================================================
3. TENANT ISOLATION
============================================================

Every inventory record must belong to the correct Store/Tenant.

Store A must never be able to:

- Read Store B stock
- Modify Store B stock
- Transfer Store B stock
- Reserve Store B stock
- View Store B warehouses
- Access Store B inventory reports
- Import Store B inventory
- Export Store B inventory

All inventory APIs, jobs, caches, events, reports, and files must
preserve tenant context.

============================================================
4. PRODUCT INVENTORY OWNERSHIP
============================================================

Inventory should normally be tracked at the sellable SKU level.

For simple products:

Product
→ Inventory

For variable products:

Product
→ Variant
→ SKU
→ Inventory

This allows each variant to maintain independent stock.

============================================================
5. INVENTORY TRACKING MODES
============================================================

The system should support configurable inventory tracking.

Potential modes:

1. Not Tracked
2. Tracked at Product Level
3. Tracked at Variant/SKU Level

Future support may include:

- Batch Tracking
- Lot Tracking
- Serial Number Tracking
- Expiry Tracking

The initial architecture must not block these extensions.

============================================================
6. STOCK QUANTITY MODEL
============================================================

- On Hand
- Reserved
- Available
- Incoming
- Committed
- Damaged where supported

AVAILABLE =
ON_HAND
-

-

============================================================
7. AUTHORITATIVE STOCK
============================================================

The server-side inventory system is authoritative.

The client must never be allowed to directly set:

- Available Stock
- Reserved Stock
- On Hand Stock

All changes must occur through authorized inventory operations.

Store

============================================================
18. TOTAL STOCK
============================================================

Total stock may be calculated as the sum of eligible warehouse
stock.

Example:

Warehouse A = 10
Warehouse B = 20
Warehouse C = 5

Total On Hand = 35

The calculation must respect inactive/archived warehouse rules.

============================================================
19. STOCK AVAILABILITY
============================================================

Available stock should account for reservations.

Example:

On Hand = 100
Reserved = 20

Available = 80

Storefront must use the authoritative available quantity or
availability status.

============================================================
20. STOCK RESERVATION
============================================================

Reservations temporarily hold inventory for an order or checkout
process.

Reservation may occur during:

- Checkout
- Order creation
- Payment processing
- Manual order workflows

Reservation rules must prevent overselling.

============================================================
21. RESERVATION LIFECYCLE
============================================================

Possible reservation states:

- PENDING
- ACTIVE
- RELEASED
- CONVERTED
- EXPIRED
- CANCELLED

Example:

Cart/Checkout
→ Reserve
→ Payment
→ Order Confirmed
→ Reservation Converted

Failed/expired checkout:
→ Reservation Released

============================================================
22. RESERVATION EXPIRY
============================================================

Reservations should have an expiry policy.

Example:

Reservation created
→ expires after configured period

Expired reservations must be released safely.

The exact duration should be configurable.

============================================================
23. CONCURRENCY CONTROL
============================================================

Inventory operations must be safe under concurrent purchases.

Example:

Stock = 1

Customer A and Customer B attempt checkout simultaneously.

The system must ensure only valid available stock is committed.

Use appropriate:

- Database transactions
- Row-level locking where appropriate
- Atomic updates
- Optimistic concurrency
- Reservation logic

============================================================
24. OVERSelling PROTECTION
============================================================

Overselling must be explicitly controlled.

Possible store setting:

Allow Overselling:
YES / NO

If disabled:

Available Stock <= 0
→ Product cannot be purchased.

If enabled:

The system must clearly represent negative or backordered stock
according to business rules.

- In Stock

37. STOCK TRANSFER
============================================================

Stock may be transferred between warehouses.

Example:

Lahore Warehouse
→ Islamabad Warehouse

TRANSFER_OUT

38. TRANSFER LIFECYCLE
============================================================

Potential states:

- DRAFT
- REQUESTED
- APPROVED

- RECEIVED
- CANCELLED

Basic stores may only require immediate transfer.

Advanced stores may use full transfer lifecycle.

============================================================
39. TRANSFER VALIDATION
============================================================

Before transfer:

- Source warehouse active
- Destination warehouse active
- Same tenant
- SKU exists
- Available stock sufficient
- Quantity valid
- Permissions valid

Cross-tenant transfers are prohibited.

============================================================
40. TRANSFER RECEIVING
============================================================

If partial quantity is received, the system must support:

- Sent Quantity

- Reason

42. INCOMING STOCK
============================================================

Incoming quantity represents expected stock not yet available.

Example:

On Hand = 20
Incoming = 50
Available = 20

The storefront should normally not count incoming stock as
available unless preorder/backorder rules explicitly allow it.

- Average Cost
- FIFO

- Standard Cost

44. COST TRACKING
============================================================

- Unit Cost
- Total Cost

45. PROFITABILITY FOUNDATION
============================================================

Inventory data may later support:

- Cost of Goods Sold
- Gross Profit
- Margin
- Stock Value

These should integrate with financial/reporting modules rather

============================================================
46. RETURNS
============================================================

Returned products may increase inventory depending on condition.

Possible return conditions:

- Resalable
- Damaged
- Used
- Defective
- Scrap

Example:

Customer Return
→ Inspection
→ Resalable → Stock In
→ Damaged → Separate/Excluded Stock

Detailed order return workflow belongs to Module 09.

============================================================
47. DAMAGED STOCK
============================================================

Damaged stock should be distinguishable from normal available
stock.

Possible approaches:

- Separate quantity state
- Separate inventory location
- Damage movement ledger

The final model must prevent damaged stock from being sold
accidentally.

============================================================
48. RESERVED VS COMMITTED STOCK
============================================================

The architecture should distinguish:

RESERVED:
Temporarily held.

COMMITTED:
Associated with a confirmed order.

ON HAND:
Physically available in inventory.

AVAILABLE:
Sellable after deductions.

This distinction becomes important for fulfillment.

============================================================
49. ORDER INTEGRATION
============================================================

Order events should affect inventory.

Example:

Order Created
→ Reserve Stock

Order Confirmed
→ Commit Stock

Order Cancelled
→ Release/Return Stock

Order Fulfilled
→ Finalize Stock Out

Exact timing must be defined in Module 09.

============================================================
50. CART INTEGRATION
============================================================

Cart should not permanently decrease On Hand stock.

If reservations are used, cart/checkout may temporarily reserve
stock according to configured policy.

Abandoned carts must not permanently lock inventory.

============================================================
51. PAYMENT INTEGRATION
============================================================

For payment-sensitive orders, inventory behavior may depend on
payment state.

Example:

COD:
Order confirmation may commit stock.

Online Payment:
Reserve during payment
→ Commit after successful payment

Failed payment:
→ Release reservation

Exact workflow will be finalized in Modules 09 and 12.

============================================================
52. SHIPPING INTEGRATION
============================================================

Fulfillment may select the warehouse based on:

- Stock availability
- Customer location
- Shipping zone
- Warehouse priority
- Delivery capability
- Cost
- Store rules

The shipping module will consume inventory availability.

============================================================
53. INVENTORY ALLOCATION
============================================================

For multi-warehouse stores, the system may allocate an order
across one or more warehouses.

Initial strategy may prefer:

1. Default Warehouse
2. Highest Stock
3. Nearest Warehouse
4. Configured Priority

The final strategy should be configurable.

54. SPLIT FULFILLMENT FOUNDATION
============================================================

55. STOCK RESERVATION ACROSS WAREHOUSES

============================================================
101. FINAL ARCHITECTURAL RULES
============================================================

1. One Core Inventory Engine.
2. All inventory data must be tenant-scoped.
3. Inventory is authoritative on the server.
4. Stock must be tracked at the correct sellable SKU level.
5. Available stock must account for reservations.
6. Critical stock changes must be transactional.
7. Overselling behavior must be explicitly configured.
8. Every stock-changing operation must be auditable.
9. Stock movements must preserve historical integrity.
10. Warehouse records must be tenant-scoped.
11. Cross-tenant transfers are prohibited.
12. Reservation lifecycle must be explicit.
13. Reservation expiry must safely release stock.
14. Duplicate inventory writes must be prevented through
    idempotency where applicable.
15. Cost data must never be exposed publicly.
16. Inventory cache must never authorize a sale.
17. Search availability must remain tenant-scoped.
18. Bulk imports/exports must be permission-controlled.
19. Offline/POS synchronization must be conflict-safe.
20. Future batch/lot/serial/expiry support must remain possible.
21. Inventory events should use reliable delivery mechanisms.
22. Package restrictions must be entitlement-driven.
23. Historical inventory data must be retained according to
    configured retention rules.
24. Inventory design must scale from one warehouse to many.
25. Inventory must integrate cleanly with Orders, Payments,
    Shipping, POS, Analytics, and future integrations.
