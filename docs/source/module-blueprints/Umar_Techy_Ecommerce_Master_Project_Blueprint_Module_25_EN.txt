1. MODULE PURPOSE
--------------------------------------------------------------------
Module 25 provides the Core Progressive Web App (PWA), Mobile Web,
Installable Store Experience, Mobile UX, Offline Presentation,
Push-Enabled Mobile Experience, Device Adaptation, and future mobile
application foundation for the Umar Techy Multi-Tenant E-Commerce
Platform.

The module extends the same Core Storefront Engine into a fast,
responsive, installable, mobile-first experience without creating a
separate business logic codebase.

Core principle:

ONE CORE COMMERCE ENGINE
        +
RESPONSIVE STOREFRONT
        +
PWA CAPABILITIES
        +
MOBILE UX
        +
SAFE OFFLINE EXPERIENCE
        +
PUSH/APP EXPERIENCE
        +
TENANT BRANDING
        +
SHARED BUSINESS RULES

--------------------------------------------------------------------
The module shall:

1. Provide PWA support.
2. Provide responsive mobile storefront behavior.
3. Support installable web applications.
4. Support web app manifests.
5. Support service workers.
6. Support safe asset caching.
7. Support offline storefront foundations.
8. Support offline-safe content access.

3. ARCHITECTURAL POSITION
--------------------------------------------------------------------
Module 25 owns:

- PWA configuration.
- Web app manifest.
- Service worker strategy.
- Offline presentation.
- Cache strategy for storefront assets.
- Install experience.
- Push subscription foundation.
- Mobile UX behavior.
- Mobile navigation.
- Device capability detection.
- PWA-specific analytics events.
- PWA health signals.

Module 25 does NOT own:

- Storefront business logic — Module 05.
- Theme system — Module 17.
- Animation runtime — Module 18.
- Notifications delivery — Module 21.
- Analytics/reporting — Module 22.
- Infrastructure execution — Module 20.
- Security policy — Module 32.
- Product/order/payment/inventory truth — Modules 06/09/12/08.

Business logic remains server-authoritative.

--------------------------------------------------------------------
PWA/mobile clients must not create an independent version of:

- Pricing.
- Discounts.
- Tax.
- Inventory.
- Shipping.
- Payment.
- Order state.
- Customer authorization.

--------------------------------------------------------------------

12. STATIC ASSET CACHING
--------------------------------------------------------------------
Suitable resources:

- CSS.
- JavaScript.
- Fonts.
- Public icons.
- Theme assets.
- Public images where appropriate.

Use immutable versioned assets where possible.


13. API CACHING
--------------------------------------------------------------------
API caching must be highly restricted.

Do not cache sensitive or rapidly changing business data casually.

Never treat cached API data as authoritative.


14. CUSTOMER DATA CACHING
--------------------------------------------------------------------
Avoid persistent caching of:

- Account details.
- Payment information.
- Private orders.
- Private addresses.
- Sensitive customer information.

If offline access is supported, use encrypted/local protected storage
and strict expiration where technically appropriate.


15. PRODUCT OFFLINE EXPERIENCE
--------------------------------------------------------------------
A limited product browsing experience may be available offline if
safe cached content exists.

Offline product data must be clearly marked as potentially stale.


16. OFFLINE STORE EXPERIENCE
--------------------------------------------------------------------
Offline experience may provide:

- Previously cached storefront.
- Previously viewed product information.
- Static pages.
- Cached navigation.
- Offline status message.
- Retry controls.

The experience must degrade gracefully.


17. OFFLINE CHECKOUT
--------------------------------------------------------------------
Offline checkout must NOT automatically create real orders unless a
future architecture explicitly provides a secure offline transaction
protocol.

Default behavior:

Offline
→ User may review cart
→ Checkout requires connectivity
→ Server validation
→ Payment/order creation

This prevents stale price, inventory, shipping, and payment state.


18. OFFLINE CART
--------------------------------------------------------------------
A local cart may be retained for UX purposes.

When reconnecting:

- Revalidate products.
- Revalidate variants.
- Revalidate prices.
- Revalidate discounts.
- Revalidate inventory.
- Revalidate shipping.
- Revalidate customer state.

Server values always win.


19. CART MERGE
--------------------------------------------------------------------
Guest offline cart may merge with an online customer cart after
authentication.

Merge must use Module 11 rules.

Conflicts must be resolved server-side.


20. OFFLINE WISHLIST
--------------------------------------------------------------------
Wishlist may have a limited local UX.

When synchronized:

- Validate product existence.
- Validate store ownership.
- Remove invalid items.
- Preserve customer authorization.


21. ONLINE/OFFLINE DETECTION
--------------------------------------------------------------------
Provide:

- Browser network state.
- Application connectivity state.
- Server reachability.

Browser "online" state alone must not be considered proof that the
application backend is reachable.


22. CONNECTION RECOVERY
--------------------------------------------------------------------
When connectivity returns:

- Refresh critical data.
- Revalidate cart.
- Refresh customer state.
- Refresh prices.
- Refresh inventory.
- Refresh promotions.
- Refresh shipping options.
- Refresh payment methods.

Avoid automatically executing sensitive actions.


23. PWA UPDATE STRATEGY
--------------------------------------------------------------------

- New version detection.
- Background download.
- Controlled activation.
- User notification.
- Safe reload.
- Rollback/recovery foundation.


24. UPDATE SAFETY
--------------------------------------------------------------------
Do not activate a new application version in a way that leaves the
user with incompatible cached application assets.


25. CACHE VERSIONING

26. MULTI-TENANT CACHE ISOLATION
--------------------------------------------------------------------

→ Store B user

- Theme configuration.
- Product content.
- Store branding.
- PWA manifest.
- Runtime API responses.

96. FINAL ARCHITECTURAL RULES
--------------------------------------------------------------------
RULE 01:
Module 25 owns PWA and mobile experience.

RULE 02:
Module 05 owns storefront business presentation and behavior.

RULE 03:
Module 17 owns themes and branding.

RULE 04:
Module 18 owns animation runtime.

RULE 05:
Module 21 owns notification delivery.

RULE 06:
Module 22 owns analytics/reporting.

RULE 07:
Module 20 owns infrastructure execution.

RULE 08:
Module 32 owns security policy.

RULE 09:
The server remains authoritative for all commerce business rules.

RULE 10:
Offline data must never be treated as authoritative for price,
inventory, tax, shipping, discount, payment, or order state.

RULE 11:
Offline checkout must require server validation and connectivity by
default.

RULE 12:
Local carts must be revalidated after reconnect.

RULE 13:
Tenant identity must be preserved in PWA configuration and caches.

RULE 14:
Cross-tenant cache leakage is a critical security failure.

RULE 15:
Private customer data must not be casually cached.

RULE 16:
Service workers must not become a second business logic engine.

RULE 17:
Service-worker updates must be versioned and safe.

RULE 18:
Old caches must be removed without breaking active sessions.

RULE 19:
PWA manifest URLs must remain tenant-safe.

RULE 20:
