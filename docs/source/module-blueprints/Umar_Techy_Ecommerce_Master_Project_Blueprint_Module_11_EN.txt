UMAR TECHY
E-COMMERCE PLATFORM
MASTER PROJECT BLUEPRINT

MODULE 11 — CART, WISHLIST & CHECKOUT
Version: 1.0
Status: Planning / Blueprint

============================================================
1. MODULE PURPOSE
============================================================

This module defines the Core Cart, Wishlist, and Checkout Engine
for the Umar Techy multi-tenant E-Commerce Platform.

The module manages the customer journey from product selection
through cart creation, wishlist management, checkout validation,
pricing calculation, inventory reservation, payment initiation,
shipping selection, and final Order creation.

Core flow:

Product
  ↓
Cart
  ↓
Checkout
  ↓
Validation
  ↓
Pricing
  ↓
Inventory Reservation
  ↓
Shipping Selection
  ↓
Payment Selection
  ↓
Order Creation
  ↓
Module 09 — Order Management

The system must support guest and registered customers and must
remain fully tenant-aware.

============================================================
2. CORE ARCHITECTURAL PRINCIPLE
============================================================

ONE CORE CART / WISHLIST / CHECKOUT ENGINE
+
STORE-SCOPED CONFIGURATION
+
SERVER-AUTHORITATIVE VALIDATION
+
REAL-TIME PRICE VALIDATION
+
INVENTORY RESERVATION
+
SECURE PAYMENT COORDINATION
+
STRICT TENANT ISOLATION

must serve every store.

Basic, Business, and Premium packages use the same engine.
Package differences are controlled through Module 04.

============================================================
3. TENANT ISOLATION
============================================================

Every:

- Cart
- Cart Item
- Wishlist
- Wishlist Item
- Checkout Session
- Checkout Token
- Shipping Selection
- Discount Evaluation
- Customer Reference
- Saved Checkout Data

must belong to the correct store/tenant.

Store A must never access Store B's carts, wishlists,
checkout sessions, customer data, pricing context, or
reserved inventory.

Tenant scope must be enforced at:

- API
- Database
- Cache
- Session
- Search
- Queue
- Events
- Logs
- Analytics
- Integrations

============================================================
4. CART TYPES
============================================================

The architecture should support:

- Guest Cart
- Registered Customer Cart
- Admin-Created Cart
- POS Cart
- API Cart
- Future Marketplace Cart

The storefront is the primary initial channel.

============================================================
5. CART OWNERSHIP
============================================================

A cart may be associated with:

- Store/Tenant
- Customer
- Anonymous Session
- User/Customer Identity Reference
- Sales Channel

A cart must have a unique secure identifier.

Public cart identifiers must not expose internal database IDs
where avoidable.

============================================================
6. GUEST CART
============================================================

Guests must be able to:

- Browse products
- Add products
- Update quantities
- Remove products
- View totals
- Proceed to checkout

Guest carts should be associated with a secure anonymous
session/token.

Guest cart data must not be accessible by guessing another
cart identifier.

============================================================
7. REGISTERED CUSTOMER CART
============================================================

Authenticated customers may have an active cart per store and
sales channel.

The cart may persist across sessions where configured.

Cart ownership must be verified on every protected request.

============================================================
8. CART LIFECYCLE
============================================================

Suggested states:

- ACTIVE
- CHECKOUT_STARTED
- CONVERTED
- ABANDONED
- EXPIRED
- MERGED
- CANCELLED

Converted carts must remain available as historical technical
records where required for audit and analytics.

============================================================
9. CART EXPIRATION
============================================================

Cart expiration should be configurable.

Expired carts should:

- Stop checkout
- Release any active reservations
- Remain available for analytics where permitted

Expired cart cleanup must be safe and tenant-scoped.

============================================================
10. CART ITEM
============================================================

Cart item should reference:

- Product
- Variant/SKU
- Quantity
- Current price context
- Added timestamp
- Selected options where applicable

The cart must not blindly trust price values sent by the client.

============================================================
11. PRODUCT VALIDATION
============================================================

When adding an item, validate server-side:

- Product exists
- Product belongs to current store
- Product is purchasable
- Product status is ACTIVE
- Product is visible to the sales channel
- Variant exists
- Variant belongs to product
- Variant is purchasable
- Package entitlement allows the feature
- Customer eligibility where applicable

============================================================
12. QUANTITY VALIDATION
============================================================

Validate:

- Positive quantity
- Integer/decimal rules based on product
- Minimum quantity
- Maximum quantity
- Quantity increments
- Per-customer purchase limits
- Available inventory
- Backorder/preorder rules

All final quantities must be server validated.

============================================================
13. CART PRICE
============================================================

Cart prices are provisional.

The server must recalculate prices during:

- Add to cart
- Cart update
- Cart retrieval where necessary
- Checkout start
- Checkout confirmation
- Order creation

The final Order price is authoritative.

============================================================
14. PRICE CHANGES
============================================================

If product pricing changes after an item enters the cart:

The system should detect the change and require the cart to be
recalculated.

Customer-facing behavior may include:

- Updated price notice
- Updated total
- Checkout recalculation

The system must never silently charge an outdated unauthorized
price.

============================================================
15. SALE PRICE
============================================================

Support:

- Regular price
- Sale price
- Scheduled sale price
- Customer/group price
- Promotion-adjusted price

Final pricing must use the authoritative pricing engine.

============================================================
16. PRODUCT VARIANTS
============================================================

Cart items must support variants.

Example:

Product:
T-Shirt

Variant:
Black / XL

The exact SKU must be stored or resolved server-side.

Inventory must operate against the correct SKU/variant.

============================================================
17. CART ATTRIBUTES
============================================================

Future-ready cart item attributes may include:

- Gift Message
- Custom Text
- Selected Add-on
- Personalization
- Service Option

Attributes must be validated against the product configuration.

============================================================
18. BUNDLES
============================================================

The cart architecture should support future product bundles.

A bundle may contain:

- Parent Product
- Child Products
- Bundle Quantity
- Bundle Pricing

Inventory behavior must be defined by the product/bundle engine.

============================================================
19. DIGITAL PRODUCTS
============================================================

The cart should be architecture-ready for digital products.

Digital products may require:

- No shipping
- Digital delivery
- Download entitlement
- Separate fulfillment

Checkout must determine whether shipping is required.

============================================================
20. SERVICE PRODUCTS
============================================================

Service products may support:

- No physical shipping
- Appointment/time selection in future
- Service area validation
- Special checkout fields

The architecture should not hard-code every cart item as a
physical shipment.

============================================================
21. MIXED CARTS
============================================================

The system should support future mixed carts containing:

- Physical Products
- Digital Products
- Services

Checkout must determine:

- Shipping requirements
- Fulfillment requirements
- Payment rules
- Tax behavior
- Delivery method

============================================================
22. CART MERGE
============================================================

When a guest logs in, the system may merge:

Guest Cart
+
Existing Customer Cart
↓
Merged Cart

Rules must prevent:

- Duplicate unintended quantities
- Invalid products
- Exceeded limits
- Inventory overselling

The customer must receive a clear result when conflicts occur.

============================================================
23. CART CONCURRENCY
============================================================

Multiple tabs/devices may update the same cart.

Use safe concurrency controls to prevent:

- Lost updates
- Invalid quantities
- Incorrect totals
- Reservation inconsistencies

============================================================
24. CART IDEMPOTENCY
============================================================

Critical cart operations should support idempotency where
repeated requests could otherwise create duplicate actions.

Examples:

- Add item
- Update quantity
- Start checkout
- Apply coupon
- Create payment intent
- Submit order

============================================================
25. CART TOTALS
============================================================

Cart totals may include:

- Subtotal
- Item Discounts
- Cart Discounts
- Shipping
- Tax
- Fees
- Store Credit
- Gift Card foundation
- Total

Exact calculation rules will integrate with Modules 12–14.

============================================================
26. MONEY PRECISION
============================================================

Money calculations must use safe decimal/fixed-precision
representation.

Do not rely on binary floating-point arithmetic for financial
calculations.

Every monetary value must have an associated currency context.

============================================================
27. CURRENCY
============================================================

Checkout must know:

- Store Currency
- Order Currency
- Currency Precision

Multi-currency is future-ready but must not create ambiguous
financial records.

The final Order currency becomes immutable after order creation
unless a controlled correction workflow exists.

============================================================
28. TAX FOUNDATION
============================================================

Checkout should calculate or consume tax according to the
store's configured tax rules.

Potential inputs:

- Product tax category
- Customer location
- Shipping location
- Store configuration
- Tax exemptions

Tax calculation must be server-authoritative.

============================================================
29. DISCOUNT INTEGRATION
============================================================

Checkout integrates with Module 14 for:

- Coupons
- Promotions
- Automatic discounts
- Customer-specific offers
- Group discounts
- Quantity discounts
- Buy X Get Y foundation

The cart must display discount results clearly.

============================================================
30. COUPON APPLICATION
============================================================

Coupon validation should check:

- Code
- Store
- Active period
- Usage limits
- Customer eligibility
- Minimum spend
- Product/category restrictions
- Exclusions
- Package entitlement

Invalid coupons must not affect the final price.

============================================================
31. COUPON REMOVAL
============================================================

Customers must be able to remove eligible coupons.

Removing a coupon must trigger a complete price recalculation.

============================================================
32. SHIPPING INTEGRATION
============================================================

Checkout integrates with Module 13.

Potential shipping methods:

- Standard Delivery
- Express Delivery
- Local Delivery
- Store Pickup
- Courier
- Free Shipping

Available methods depend on:

- Store
- Destination
- Cart contents
- Weight
- Dimensions
- Delivery zone
- Order value
- Product restrictions

============================================================
33. SHIPPING ADDRESS
============================================================

Checkout must support:

- Existing saved address
- New address
- Guest address

The final Order must receive an immutable address snapshot.

============================================================
34. BILLING ADDRESS
============================================================

Billing address may:

- Match shipping address
- Be different

The checkout flow must explicitly support the selected mode.

============================================================
35. ADDRESS VALIDATION
============================================================

Before order creation:

- Required fields
- Valid country
- Province/state
- City

- Phone
- Shipping serviceability

must be validated.

============================================================
36. SHIPPING CALCULATION
============================================================

Shipping price must be recalculated server-side using:

- Destination
- Cart
- Weight
- Dimensions
- Delivery zone
- Shipping method
- Store rules
- Promotions

Client-submitted shipping cost must never be trusted.

37. PAYMENT INTEGRATION
============================================================

Checkout integrates with Module 12.

Initial payment methods may include:

- Cash on Delivery
- Bank Transfer
- JazzCash
- Easypaisa
- Other supported gateways

Future gateways can be added through a provider abstraction.

============================================================
38. CASH ON DELIVERY
============================================================

COD checkout may require:

- Customer contact
- Address validation
- Order value limits
- COD availability
- Risk rules
- Shipping area eligibility

COD orders must still pass inventory and order validation.

============================================================
39. BANK TRANSFER
============================================================

Bank transfer checkout may create an order with:

Payment Status:
PENDING

The store may later confirm payment.

Customers must receive clear instructions without exposing
sensitive internal financial data.

40. ONLINE PAYMENT

Payment Intent / Transaction

41. PAYMENT CALLBACK SECURITY
============================================================

Payment callbacks must use:

- Signature verification
- Provider verification
- Transaction reference validation
- Amount validation
- Currency validation
- Store validation
- Idempotency

A callback for Store A must never update Store B.

Checkout should use a dedicated Checkout Session.

Potential fields:

- Checkout ID

- CREATED
- ADDRESS_PENDING

- REVIEW
- PROCESSING
- COMPLETED
- EXPIRED
- CANCELLED
- FAILED

The exact state machine must be finalized before implementation.

============================================================
44. CHECKOUT EXPIRY
============================================================

Checkout sessions should expire after a configurable period.

Expired sessions must not create orders without fresh validation.

Any associated temporary reservations must be released.

============================================================
45. CHECKOUT SNAPSHOT
============================================================

At checkout review, the system may show a calculated snapshot.

However, the final Order must still perform authoritative
server-side validation before creation.

============================================================
46. FINAL VALIDATION
============================================================

Before creating an Order, validate again:

- Store status
- Customer status
- Product status
- Variant status
- Product availability
- Quantity
- Price
- Discount
- Coupon
- Tax
- Shipping
- Payment method
- Currency
- Address
- Inventory
- Package entitlement
- Usage limits

============================================================
47. INVENTORY RESERVATION
============================================================

Inventory reservation must happen safely during checkout/order
coordination.

Conceptual flow:

Cart
↓
Checkout
↓
Validate Stock
↓
Create Reservation
↓
Payment / Order Coordination
↓
Commit or Release

Module 08 remains the source of truth for inventory.

============================================================
48. RESERVATION EXPIRY
============================================================

Temporary reservations must have an expiry policy.

If checkout fails or expires:

Reservation
→ RELEASED

If order succeeds:

Reservation
→ CONVERTED / COMMITTED

This prevents stock from remaining permanently locked.

============================================================
49. OVERSelling PREVENTION
============================================================

Checkout must prevent overselling through:

- Transactional inventory checks
- Reservations
- Concurrency controls
- Server-authoritative stock
- Idempotent order creation

Never rely on storefront stock display alone.

============================================================
50. OUT-OF-STOCK DURING CHECKOUT
============================================================

If stock becomes unavailable:

- Stop order creation for the affected quantity
- Release any invalid reservation
- Show clear customer message
- Recalculate cart
- Allow customer to modify cart

============================================================
51. ORDER CREATION
============================================================

Final flow:

Validated Checkout
↓
Inventory Coordination
↓
Payment Coordination
↓
Create Order
↓
Create Order Items
↓
Create Financial Totals
↓
Create Historical Snapshots
↓
Commit Inventory
↓
Publish Outbox Events
↓
Send Notifications

Module 09 owns the final Order model and lifecycle.

============================================================
52. ATOMICITY
============================================================

Critical checkout/order operations must use transactional
boundaries appropriate to the architecture.

The system must prevent:

- Paid order without order record
- Order without inventory handling
- Duplicate order
- Duplicate payment capture
- Incorrect reservation conversion

Distributed provider operations must use reliable reconciliation
and idempotency rather than assuming a single database
transaction can control external systems.

============================================================
53. ORDER DUPLICATION PREVENTION
============================================================

Use:

- Idempotency keys
- Checkout session identity
- Payment transaction references
- Unique constraints
- Server-side state checks

Repeated submit requests must not create duplicate orders.

============================================================
54. CHECKOUT RETRY
============================================================

If payment fails:

Customer should be able to retry where safe.

The system should avoid creating multiple orders for a single
checkout attempt unless explicitly intended.

============================================================
55. FAILED PAYMENT
============================================================

Payment failure should:

- Record failure
- Preserve useful checkout state
- Release or maintain reservation according to policy
- Allow retry
- Avoid false order confirmation

============================================================
56. SUCCESSFUL PAYMENT
============================================================

Payment success must be reconciled with:

- Checkout
- Store
- Customer
- Amount
- Currency
- Payment transaction
- Order

Only verified payment state may trigger payment confirmation.

============================================================
57. ORDER CONFIRMATION
============================================================

After successful order creation, customer may receive:

- Order Number
- Items
- Total
- Payment Status
- Fulfillment Status
- Shipping Method
- Delivery Address summary
- Estimated delivery information
- Tracking information when available

============================================================
58. CHECKOUT ERROR HANDLING
============================================================

Errors must be actionable.

Examples:

- Product no longer available
- Quantity unavailable
- Price changed
- Coupon expired
- Shipping unavailable
- Payment failed
- Address invalid
- Store temporarily unavailable

Do not expose internal stack traces or sensitive system details.

============================================================
59. CHECKOUT SECURITY
============================================================

Protect against:

- Cart ID manipulation
- Customer ID manipulation
- Price manipulation
- Quantity manipulation
- Coupon manipulation
- Shipping price manipulation
- Payment amount manipulation
- Tenant crossing
- Session theft
- Replay attacks
- Duplicate submissions
- CSRF where applicable
- Bot abuse

- Scoped to the store

============================================================
64. WISHLIST PURPOSE
============================================================

Wishlist allows customers to save products for future interest.

It is separate from the active cart.

Wishlist must not reserve inventory.

============================================================
65. WISHLIST TYPES
============================================================

Initial:

- Default Wishlist

Future:

- Multiple Wishlists
- Shared Wishlist
- Gift Wishlist
- Private/Public Wishlist

============================================================
66. WISHLIST ITEM
============================================================

Wishlist item may reference:

- Product
- Variant where appropriate
- Customer
- Store
- Added At

The product must be revalidated when displayed or moved to cart.

============================================================
67. WISHLIST AVAILABILITY
============================================================

Wishlist may show:

- Available
- Out of Stock
- Hidden
- Archived
- Price Changed

The wishlist must not assume that a saved product remains
purchasable forever.

============================================================
68. WISHLIST TO CART
============================================================

Customer may move a wishlist item to cart.

The system must perform full product, variant, price, inventory,
and entitlement validation.

============================================================
69. WISHLIST GUEST SUPPORT
============================================================

Guest wishlist may be supported through local/device storage
where appropriate.

customer data unless explicitly created server-side.

============================================================
70. WISHLIST LOGIN MERGE
============================================================

When a guest becomes authenticated, wishlist items may merge.

Duplicates should be safely de-duplicated.

Invalid or unavailable products should not create invalid cart
items.

- Wishlist availability

104. FINAL ARCHITECTURAL RULES
============================================================

1. One Core Cart, Wishlist, and Checkout Engine.
2. Every resource must be tenant-scoped.
3. Guest checkout must be supported.
4. Registered customers must have persistent cart support where
   configured.
5. Cart prices are provisional.
6. Final prices must be server-calculated.
7. Client-submitted prices must never be trusted.
8. Shipping charges must be server-calculated.
9. Tax must be server-authoritative.
10. Coupon eligibility must be server-authoritative.
11. Inventory must remain authoritative in Module 08.
12. Inventory reservations must be concurrency-safe.
13. Checkout expiry must release temporary reservations.
14. Payment success must be verified server-side.
15. Payment callbacks must be authenticated and idempotent.
16. Duplicate checkout submissions must not create duplicate
    orders.
17. Final Order creation belongs to Module 09.
18. Historical Order snapshots must be created during order
    creation.
19. Wishlist must never reserve inventory.
20. Wishlist-to-cart must perform full validation.
21. Guest-to-account cart merge must be safe and deterministic.
22. Private cart and checkout data must never be publicly cached.
23. Customer ownership must be enforced on every protected
    customer request.
24. Checkout must support physical, digital, and service products
    through an extensible fulfillment model.
25. The system must remain ready for future payment gateways,
    shipping providers, loyalty, subscriptions, marketplace,
    POS, AI, and mobile/PWA channels.
26. All financial operations must use safe monetary precision.
27. All critical operations must support idempotency and reliable
    recovery.
28. Security, privacy, tenant isolation, and auditability are
    mandatory non-functional requirements.
