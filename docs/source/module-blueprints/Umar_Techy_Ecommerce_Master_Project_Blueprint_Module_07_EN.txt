UMAR TECHY
E-COMMERCE PLATFORM
MASTER PROJECT BLUEPRINT

MODULE 07 — CATEGORY, BRAND & ATTRIBUTE MANAGEMENT
Version: 1.0
Status: Planning / Blueprint

============================================================
1. MODULE PURPOSE
============================================================

This module defines the reusable architecture for organizing
products through:

- Categories
- Subcategories
- Brands
- Attributes
- Attribute Groups
- Attribute Values
- Variant Options
- Product Filters
- Collections integration
- Merchandising structure
- Navigation structure
- SEO structure
- Tenant-specific catalog taxonomy

The module must work as part of the ONE Core E-Commerce
Platform and support thousands of independent stores without
creating separate codebases.

============================================================
2. CORE PRINCIPLE
============================================================

ONE CORE TAXONOMY ENGINE
+
TENANT-SCOPED CATALOG STRUCTURE
+
CONFIGURABLE ATTRIBUTES
+
REUSABLE FILTERING
+
PACKAGE ENTITLEMENTS

must serve every store.

Basic, Business, and Premium stores use the same underlying
taxonomy engine.

Commercial differences are enforced through Module 04.

============================================================
3. TENANT ISOLATION
============================================================

Every tenant-owned category, brand, attribute, value, and
taxonomy configuration must belong to exactly one Store/Tenant.

Store A must never be able to:

- Read Store B categories
- Modify Store B categories
- Delete Store B brands
- Read Store B attributes
- Read Store B attribute values
- Search Store B taxonomy
- Use Store B private taxonomy configuration

Public/global platform records must be explicitly distinguished
from tenant-owned records.

============================================================
4. GLOBAL VS TENANT TAXONOMY
============================================================

The architecture should support:

GLOBAL PLATFORM DEFINITIONS:

- System attribute types
- Approved measurement types
- Global system defaults
- Platform taxonomy templates
- Future marketplace taxonomy definitions

TENANT DATA:

- Categories
- Category hierarchy
- Brands
- Attributes
- Attribute Groups
- Attribute Values
- Filter configuration
- Navigation assignment
- Store-specific taxonomy settings

A future store may optionally import a platform-approved
template into its own tenant data.

============================================================
5. CATEGORY DEFINITION
============================================================

A Category represents a logical group of products.

Example:

Fashion
  ├── Men
  │    ├── Shirts
  │    └── Shoes
  └── Women
       ├── Dresses
       └── Bags

Core category fields may include:

- Category ID
- Store/Tenant ID
- Parent Category ID
- Name
- Slug
- Description
- Image
- Banner
- Status
- Visibility
- Sort Order
- SEO Metadata
- Created At
- Updated At
- Archived At

============================================================
6. CATEGORY HIERARCHY
============================================================

Categories should support multiple levels.

Example:

Electronics
  └── Mobile Phones
       └── Android Phones
            └── Samsung

The platform should not unnecessarily hard-code only two or
three levels.

A configurable maximum depth may be enforced for performance
and usability.

============================================================
7. CATEGORY TREE
============================================================

The system must efficiently represent and retrieve category
trees.

Required operations:

- Create Child
- Move Category
- Rename
- Reorder
- Hide
- Publish
- Archive
- Restore
- Retrieve Ancestors
- Retrieve Descendants
- Retrieve Breadcrumbs

Category tree operations must preserve tenant boundaries.

============================================================
8. CATEGORY PARENTING RULES
============================================================

A category:

- May have zero or one parent
- Must not become its own parent
- Must not create circular hierarchy
- Must belong to the same tenant as its parent
- Must not be moved across tenants

The system must validate hierarchy changes before saving.

============================================================
9. CATEGORY ROOT
============================================================

Each store may have multiple root categories.

Example:

Men
Women
Kids
Accessories

A virtual root may be used internally to simplify hierarchy
management.

- DRAFT

25. BRAND PRODUCT ASSIGNMENT

English:

Urdu:

============================================================
39. VARIANT OPTIONS
============================================================

Some attributes become customer-selectable variant options.

Example:

Product:
T-Shirt

Variant Options:
- Color
- Size

Not every product attribute must create a variant.

============================================================
40. ATTRIBUTE VS VARIANT OPTION
============================================================

This distinction is mandatory.

ATTRIBUTE:
Describes a product.

Example:
Material = Cotton

VARIANT OPTION:
Changes the sellable configuration.

Example:
Color = Black
Size = Large

The architecture must not treat every attribute as a variant.

============================================================
41. PRODUCT ATTRIBUTE ASSIGNMENT
============================================================

Products may assign attributes such as:

Material = Cotton
Weight = 500g
Waterproof = Yes

Assignments should support appropriate type validation.

============================================================
42. PRODUCT VARIANT OPTION ASSIGNMENT
============================================================

Variants may reference option values.

Example:

Product:
Shirt

Variant:
Black / Large

References:
Color = Black
Size = Large

The combination must be valid for the parent product.

============================================================
43. OPTION COMBINATION UNIQUENESS
============================================================

A product must not contain duplicate variant combinations.

Example:

Black + Large

must not exist twice under the same product.

The database and application layer should both help enforce
this rule.

============================================================
44. ATTRIBUTE SETS
============================================================

Example:

- Processor
- RAM
- Storage

Attribute Sets reduce repetitive administration.

118. FINAL ARCHITECTURAL RULES
============================================================

1. One Core Taxonomy Engine.
2. All tenant taxonomy data must have explicit tenant ownership.
3. Categories must support hierarchical structure.
4. Circular category relationships are prohibited.
5. Category moves must be validated transactionally where possible.
6. Category slugs must be tenant-scoped.
7. Brands must be tenant-scoped.
8. Attributes must be reusable.
9. Attributes and variant options are not the same concept.
10. Variant combinations must be unique per product.
11. Attribute values must belong to their attribute.
12. Category-specific attributes must be supported.
13. Filter configuration must be tenant-specific.
14. Public taxonomy APIs must expose only public data.
15. Cache keys must include tenant context.
16. Search indexes must include tenant context.
17. Deletion must preserve historical integrity.
18. Bulk operations require authorization.
19. Imports must validate before committing.
20. Exports must be tenant-scoped.
21. Taxonomy content must be sanitized.
22. AI suggestions must not perform destructive actions silently.
23. Taxonomy templates must create tenant-owned copies.
24. Package limits must be entitlement-driven.
25. Architecture must remain extensible for future marketplace,
    POS, mobile, API, and AI channels.
