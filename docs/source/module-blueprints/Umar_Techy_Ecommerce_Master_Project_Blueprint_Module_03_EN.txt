MODULE 03 — MULTI-TENANT & STORE MANAGEMENT
Version: 1.0

============================================================
1. MODULE PURPOSE
============================================================

This module defines the Multi-Tenant and Store Management
foundation of the Umar Techy E-Commerce Platform.

This is one of the most critical modules in the entire system.

The platform must be built once and operate as a shared
Multi-Tenant SaaS platform capable of serving many independent
e-commerce stores.

A new customer must receive a new Store/Tenant within the
existing platform rather than requiring a new software project,
new application codebase, or manually rebuilt e-commerce system.

The module is responsible for:

- Store creation
- Store lifecycle
- Tenant isolation
- Store identity
- Store configuration
- Store ownership
- Store status
- Store onboarding
- Store package association
- Store domain association
- Store branding configuration
- Store operational settings
- Store suspension / reactivation
- Store deletion / archival rules
- Platform-level store management

============================================================
2. CORE PRINCIPLE
============================================================

ONE CORE PLATFORM
+
MANY INDEPENDENT STORES
+
STRICT TENANT ISOLATION
+
CENTRALIZED PLATFORM MANAGEMENT
+
STORE-SPECIFIC CONFIGURATION
+
PACKAGE-BASED ENTITLEMENTS

The Core Application is shared.

Business data and store configuration are tenant-scoped.

No store should require a separate source-code copy merely
because it belongs to a different customer.

============================================================
3. WHAT IS A TENANT?
============================================================

A Tenant represents an independent business environment within
the Umar Techy E-Commerce Platform.

For the initial product model:

One Store = One Primary Tenant

The architecture should remain flexible enough to support
future relationships such as:

- One customer owning multiple stores
- One user managing multiple stores
- Reseller-managed stores
- Multiple brands under a business account
- Multi-store enterprise customers

Each tenant must have a unique internal identifier.

Example:

Tenant ID: T000001
Store ID: S000001

The final identifier strategy will be defined in the
Database Blueprint.

============================================================
4. STORE VS USER
============================================================

The platform must maintain a clear separation between:

USER ACCOUNT
and
STORE / TENANT

A user represents an identity.

A store represents a business environment.

A user gains access to a store through a membership relationship.

Example:

User A
|
+-- Store A → Owner
+-- Store B → Manager

This architecture must align with Module 02.

============================================================
5. STORE CREATION MODELS
============================================================

The platform should support two primary store creation methods.

A. PLATFORM-ASSISTED CREATION

Umar Techy staff creates a store for a customer.

B. SELF-SERVICE CREATION

Customer signs up and creates a store through the onboarding
process.

The same underlying Store Creation Service should be used by
both flows wherever practical.

This prevents two separate store creation systems from
developing different behavior.

7. STORE LIFECYCLE
============================================================

The store must have a controlled lifecycle.

Suggested states:

- PROVISIONING
- ONBOARDING
- TRIAL
- ACTIVE
- GRACE_PERIOD
- SUSPENDED
- CANCELLED
- ARCHIVED
- DELETING

State transitions must be controlled by business rules.

A store should never move directly between arbitrary states

============================================================
8. STORE STATUS DEFINITIONS
============================================================

PROVISIONING

Store resources and configuration are being created.

ONBOARDING

Store exists but setup is incomplete.

TRIAL

Store is operating under a trial entitlement.

ACTIVE

Store is fully operational under a valid package/subscription.

GRACE_PERIOD

Subscription or required service has expired but limited
recovery time remains.

SUSPENDED

Storefront and/or administrative access is restricted
according to suspension rules.

CANCELLED

Customer has cancelled the service.

ARCHIVED

Store is retained for historical or recovery purposes but is
not operational.

DELETING

Store is undergoing an approved deletion workflow.

============================================================
9. TENANT ISOLATION — NON-NEGOTIABLE
============================================================

Tenant isolation is a core security requirement.

A tenant must not be able to:

- Read another tenant's products
- Read another tenant's customers
- Read another tenant's orders
- Modify another tenant's data
- Delete another tenant's data
- Search another tenant's data
- Export another tenant's data
- Access another tenant's files
- Access another tenant's media
- Access another tenant's reports
- Access another tenant's backups
- Access another tenant's API credentials
- Access another tenant's settings

Tenant isolation must be enforced server-side.

Client-side filtering is never sufficient.

============================================================
10. TENANT CONTEXT
============================================================

Every tenant-scoped request must execute within a trusted
tenant context.

Tenant context should be derived from authenticated identity,
authorized membership, and the requested store/domain context.

The system must never trust tenant identity solely from:

- Query parameters
- URL segments
- Request body
- Hidden fields
- Client-side state
- Cookies without server validation

Every tenant context must be validated.

The final database strategy will be determined in the

12. TENANT-SCOPED DATA RULE
============================================================

Any entity that belongs to a store must have an explicit,
consistent relationship to that tenant.

A tenant-scoped query must enforce the tenant boundary.

Example conceptual rule:

WHERE TenantId = CurrentAuthorizedTenantId

The actual implementation must use safe centralized patterns
to reduce the risk of accidentally omitting tenant filtering.

30. STORE PACKAGE ASSOCIATION
============================================================

Each store must be associated with a package/subscription state.

Example:

Store A → BASIC
Store B → BUSINESS
Store C → PREMIUM

Package entitlement must be evaluated centrally.

Changing a package should not create a new store.

The same Store/Tenant identity remains intact.

============================================================
31. PACKAGE UPGRADE / DOWNGRADE
============================================================

When a store upgrades:

- Store ID remains unchanged.
- Tenant remains unchanged.
- Existing data remains.
- New entitlements become available.

When a store downgrades:

- Store ID remains unchanged.
- Existing data should not be silently destroyed.
- Restricted features become unavailable.
- The system should identify data exceeding new limits.
- Customer must receive clear guidance for resolution.

The exact downgrade policy will be defined in Module 04.

35. STORE CANCELLATION
============================================================

Potential stages:

CANCELLED
→ RETENTION / GRACE
→ ARCHIVED
→ OPTIONAL PERMANENT DELETION

============================================================
36. STORE ARCHIVAL
============================================================

Archived stores should retain required historical information
while remaining unavailable for normal operation.

Archive strategy should consider:

- Orders
- Financial records
- Audit records
- Customer records
- Subscription history
- Domain history
- Backup references

Archived data must remain protected.

============================================================
37. STORE DELETION
============================================================

Permanent deletion must be treated as a high-risk operation.

Requirements should include:

- Explicit authorization
- Confirmation
- Grace period
- Audit trail
- Backup policy
- Dependency checks
- Data retention rules
- Safe asynchronous deletion
- Final verification

The system must not expose a simple destructive action that
can accidentally erase an entire store immediately.

============================================================
42. STORE MEDIA ISOLATION
============================================================

Store media must be tenant-scoped.

Examples:

- Product images
- Store logo
- Banner images
- Content images
- Documents

A Store A media URL or identifier must not allow Store B
to access Store A's private media.

Public product images may be publicly accessible where
intended, but private storage and administrative media must
remain protected.

============================================================
43. STORE CACHING ISOLATION
============================================================

Caching must never mix tenant-specific content.

The cache key design must include appropriate tenant/store
context.

Examples:

- Store configuration cache
- Product cache
- Category cache
- Theme configuration cache
- Storefront page cache

A cached Store A response must never be returned for Store B.

============================================================
44. SEARCH ISOLATION
============================================================

Search indexes must preserve tenant boundaries.

If a shared search infrastructure is used, tenant identity
must be part of the indexing and query authorization model.

A search request must never return products, customers,
orders, or other private information from another tenant.

============================================================
45. QUEUE & JOB ISOLATION
============================================================

Background jobs must preserve tenant context.

Examples:

- Order notifications
- Inventory updates
- Scheduled reports
- Backup jobs
- Subscription jobs
- Domain reminders
- AI processing
- Import jobs
- Export jobs

Every tenant-scoped job must carry sufficient context to
process only the intended store.

============================================================
46. WEBHOOK ISOLATION
============================================================

Incoming and outgoing webhooks must be associated with the
correct tenant.

Webhook processing must validate:

- Source
- Signature
- Tenant
- Event Type
- Authorization
- Idempotency

A webhook intended for Store A must never update Store B.

============================================================
47. RATE LIMITING
============================================================

Rate limiting should consider:

- User
- Store / Tenant
- IP
- API Key
- Endpoint
- Operation Type

Limits may differ by package and infrastructure capacity.

Security rate limits must not be bypassed by changing tenant
identifiers.

============================================================
52. STORE TEMPLATE / CLONING CONCEPT
============================================================

A future store cloning or template system may allow authorized
users to create a new store based on an existing configuration.

However:

- Customer data must never be copied unintentionally.
- Orders must not be cloned unless explicitly supported.
- Customer accounts must not be copied by default.
- Private credentials must never be copied.
- Tenant IDs must always be regenerated.
- Domains must never be duplicated.
- Package and subscription must be independently assigned.

This should be implemented only through a controlled workflow.

============================================================
62. SECURITY NON-NEGOTIABLES
============================================================

- Never trust client-provided tenant IDs.
- Never allow cross-tenant queries.
- Never allow cross-tenant media access.
- Never allow cross-tenant exports.
- Never allow cross-tenant background processing.
- Never allow cross-tenant search results.
- Never allow package restrictions to be bypassed.
- Never expose tenant secrets to another tenant.
- Never allow unauthorized ownership transfer.
- Never allow support access without proper authorization.
- Never delete stores through an unsafe one-step operation.
- Never mix tenant-specific cache entries.
- Never allow domain routing to resolve to the wrong tenant.
- Never log sensitive credentials.
