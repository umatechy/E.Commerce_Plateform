UMAR TECHY
E-COMMERCE PLATFORM
MASTER PROJECT BLUEPRINT

MODULE 12 — PAYMENT MANAGEMENT & GATEWAYS
Version: 1.0
Status: Planning / Blueprint

============================================================
1. MODULE PURPOSE
============================================================

This module defines the Core Payment Management and Gateway
architecture for the Umar Techy multi-tenant E-Commerce Platform.

The payment system must provide one unified payment layer capable
of supporting multiple stores, multiple payment methods, multiple
providers, refunds, reconciliation, callbacks/webhooks, COD,
bank transfer, future gateways, and secure financial state
management.

Core principle:

ONE CORE PAYMENT ENGINE
+
MULTIPLE PAYMENT METHODS
+
MULTIPLE PROVIDERS
+
STORE-SPECIFIC CONFIGURATION
+
TENANT ISOLATION
+
SERVER-AUTHORITATIVE FINANCIAL STATE

============================================================
2. PAYMENT ARCHITECTURE PRINCIPLE
============================================================

The platform must NOT hard-code one payment provider into the
checkout system.

Instead:

Checkout
   ↓
Payment Service
   ↓
Payment Method
   ↓
Provider Adapter
   ↓
Gateway / Manual Method
   ↓
Payment Result
   ↓
Verified Transaction
   ↓
Order Payment State

This allows new providers to be added without rewriting the
Checkout or Order engines.

============================================================

4. PROVIDER ABSTRACTION
============================================================

Every gateway/provider should implement a common abstraction.

Conceptual operations:

- Initialize Payment
- Create Payment Intent
- Redirect/Hosted Payment
- Verify Payment
- Capture Payment
- Void Payment
- Refund Payment
- Get Transaction
- Handle Callback
- Handle Webhook
- Reconcile Transaction

Not every provider supports every operation.

The provider capability matrix must explicitly define supported
operations.

============================================================
6. PAYMENT VS ORDER
============================================================

Order and Payment are separate concepts.

One Order may have:

- One Payment
- Multiple Payment Attempts
- Multiple Transactions
- Partial Payments
- Multiple Refunds

The Order remains authoritative for commercial order state.

The Payment Engine remains authoritative for payment transaction
state.

============================================================
7. PAYMENT STATUS
============================================================

Suggested states:

- CREATED
- PENDING
- REQUIRES_ACTION
- AUTHORIZED
- PAID
- PARTIALLY_PAID
- FAILED
- CANCELLED
- EXPIRED
- REFUND_PENDING
- PARTIALLY_REFUNDED
- REFUNDED
- DISPUTED
- REVERSED

Provider-specific states must map into the platform state model.

============================================================
8. PAYMENT ATTEMPT
============================================================

A payment attempt records an individual attempt.

Potential fields:

- Attempt ID
- Payment ID
- Order ID
- Provider
- Method
- Amount
- Currency
- Status
- Started At
- Completed At
- Failure Code
- Failure Reason
- Provider Reference

This allows retry without overwriting historical attempts.

============================================================
9. PAYMENT TRANSACTION
============================================================

Transactions should be immutable financial records wherever
possible.

Potential transaction types:

- AUTHORIZATION
- CAPTURE
- SALE
- VOID
- REFUND
- PARTIAL_REFUND
- REVERSAL
- ADJUSTMENT

Every transaction must be auditable.

============================================================
10. INTERNAL VS PROVIDER REFERENCES
============================================================

Use separate identifiers:

Internal Payment ID
Internal Transaction ID
Provider Payment ID
Provider Transaction ID

Provider identifiers must not replace internal identifiers.

============================================================
11. PAYMENT AMOUNT
============================================================

Payment amount must be calculated server-side.

The server must validate:

- Order total
- Currency
- Discounts
- Shipping
- Tax
- Fees
- Store credit
- Previous payments
- Refunds

The client must never determine the final payable amount.

============================================================
12. PAYMENT CURRENCY
============================================================

Every payment must include:

- Currency Code
- Amount
- Currency Precision

The provider request must use the exact validated currency.

Currency mismatches must fail safely.

============================================================
13. PAYMENT CALCULATION
============================================================

Conceptual:

Order Total
− Applied Payments
+ Required Adjustments
− Eligible Store Credit
=
Remaining Payable Amount

The exact financial model must be defined in the financial
blueprints.

============================================================
14. ZERO-VALUE ORDERS
============================================================

If an order becomes fully discounted or otherwise has zero
payable amount:

The payment engine may mark payment as:

PAID / NO_PAYMENT_REQUIRED

according to the final financial rules.

No external gateway should be called for zero-value orders.

============================================================
15. CASH ON DELIVERY
============================================================

COD is a payment method, not an online gateway.

Flow:

Checkout
↓
COD Eligibility
↓
Order Created
↓
Payment Status = UNPAID
↓
Fulfillment / Delivery
↓
Cash Collected
↓
Payment Recorded
↓
Payment Status = PAID

COD collection must be recorded as an auditable transaction.

============================================================
16. COD ELIGIBILITY
============================================================

Store configuration may define:

- Minimum order value
- Maximum order value
- Supported areas
- Product restrictions
- Customer restrictions
- COD fee
- Customer risk controls
- Package availability

============================================================
17. COD RISK FOUNDATION
============================================================

Potential risk signals:

- Repeated failed deliveries
- Excessive COD cancellations
- High-value COD
- Repeated suspicious addresses
- Excessive order velocity

Risk assessment should be separate from payment state.

============================================================
18. BANK TRANSFER
============================================================

Bank transfer is a manual or semi-automated payment method.

Flow:

Checkout
↓
Order Created
↓
Payment Status = PENDING
↓
Customer Receives Bank Details
↓
Customer Transfers Money
↓
Proof / Reference Submitted where supported
↓
Staff / Bank Integration Verification
↓
Payment Confirmed

============================================================
19. BANK TRANSFER VERIFICATION
============================================================

Authorized staff may verify:

- Amount
- Bank account
- Transfer reference
- Transfer date
- Order
- Customer

Confirmation must be audited.

Customer-submitted screenshots must not automatically mark
payments as paid.

============================================================
20. JAZZCASH
============================================================

JazzCash should be integrated through the provider abstraction.

The integration must support only the capabilities actually
provided by the selected JazzCash integration method.

Required controls:

- Merchant credentials
- Signature/security validation
- Amount validation
- Currency validation
- Order reference validation
- Callback verification
- Idempotency
- Reconciliation

Credentials must never be exposed to customers.

============================================================
21. EASYPaisa
============================================================

Easypaisa should use the same provider abstraction.

Required controls:

- Merchant credentials
- Secure configuration
- Transaction reference
- Amount validation
- Callback verification
- Idempotency
- Reconciliation

Exact API behavior depends on the selected official provider
integration.

============================================================
22. FUTURE CARD PAYMENTS
============================================================

The architecture should support card gateways without storing
raw card credentials.

Preferred approach:

Customer
↓
Gateway Hosted UI / Secure Tokenization
↓
Provider Token
↓
Payment Transaction

The platform should not store prohibited raw card data.

============================================================
23. TOKENIZED PAYMENT METHODS
============================================================

Future saved payment methods may store:

- Provider Token
- Provider Customer Reference
- Card Brand where safely provided
- Last Four Digits where permitted
- Expiry Metadata where permitted

Never store raw card number or CVV in the core platform.

============================================================
24. PAYMENT INTENT
============================================================

For gateways supporting payment intents:

Checkout
↓
Create Payment Intent
↓
Customer Action
↓
Provider Processing
↓
Verified Result
↓
Capture / Confirmation
↓
Order Payment Update

Payment Intent must be tenant and order scoped.

============================================================
25. REDIRECT PAYMENT
============================================================

For hosted checkout gateways:

1. Create internal payment attempt
2. Create provider transaction
3. Redirect customer
4. Customer completes payment
5. Provider returns customer
6. Server verifies transaction
7. Update payment state
8. Confirm order state

The browser redirect alone is not authoritative.

============================================================
26. WEBHOOKS
============================================================

Provider webhooks are critical.

Webhook processing must validate:

- Provider signature
- Provider account
- Transaction reference
- Store
- Order
- Amount
- Currency
- Event type

Webhook processing must be idempotent.

============================================================
27. CALLBACK VS WEBHOOK
============================================================

Customer browser callback:

Useful for user experience.

Server webhook/provider verification:

Authoritative source where supported.

Never mark a payment successful solely because a customer
returned to the success URL.

============================================================
28. WEBHOOK IDEMPOTENCY
============================================================

Duplicate webhook delivery must not create duplicate:

- Payments
- Captures
- Refunds
- Order updates
- Notifications

Store provider event IDs where available.

============================================================
29. WEBHOOK REPLAY PROTECTION
============================================================

Protect against:

- Old webhook replay
- Modified payload
- Forged provider request
- Duplicate event

Use:

- Signature verification
- Timestamp validation where supported
- Event ID uniqueness
- Transaction state checks

============================================================
30. PAYMENT SIGNATURE VALIDATION
============================================================

Where provider signatures exist:

Raw Payload
+
Provider Secret
↓
Signature Verification
↓
Trusted Event

Never trust a client-generated signature.

============================================================
31. PAYMENT PROVIDER CONFIGURATION
============================================================

Store-specific provider configuration may include:

- Enabled/Disabled
- Merchant ID
- API Key
- Secret
- Public Key
- Environment
- Callback URL
- Webhook Secret
- Currency
- Limits
- Supported methods

Secrets must be encrypted or stored in an appropriate secure
secret-management mechanism.

============================================================
32. TEST VS PRODUCTION
============================================================

Each provider should support environment separation where
available:

- SANDBOX
- PRODUCTION

Production credentials must never be used in automated tests.

============================================================
33. SECRET MANAGEMENT
============================================================

Payment secrets must:

- Never be committed to Git
- Never appear in source code
- Never appear in client applications
- Never appear in normal logs
- Never be returned by APIs
- Be access-controlled
- Be rotated where supported

============================================================
34. STORE-SPECIFIC PROVIDER ACCOUNTS
============================================================

Different stores may use different merchant accounts.

Example:

Store A → JazzCash Account A
Store B → JazzCash Account B

Provider configuration must therefore be tenant-scoped.

→

41. MULTIPLE PAYMENT ATTEMPTS
============================================================

An order may have:

Attempt 1 → Failed
Attempt 2 → Failed
Attempt 3 → Successful

============================================================
42. PAYMENT RETRY
============================================================

Retry must:

- Create a new attempt where appropriate
- Preserve previous failure
- Revalidate order
- Revalidate amount
- Revalidate currency
- Revalidate payment method
- Revalidate order state

============================================================
43. PAYMENT EXPIRATION
============================================================

Payment sessions may expire.

Expired payment attempts must not later become successful without
provider verification and state reconciliation.

============================================================
44. PAYMENT CANCELLATION
============================================================

Cancellation must consider provider capabilities.

Possible:

- Cancel pending payment
- Void authorization
- Cancel payment intent
- Mark manual payment cancelled

Never assume every provider supports cancellation.

============================================================
45. AUTHORIZATION AND CAPTURE
============================================================

Future card providers may support:

Authorization
→
Capture

The architecture must distinguish:

AUTHORIZED
from
PAID/CAPTURED

============================================================
46. PAYMENT REFUNDS
============================================================

Refunds are linked to payments.

Refund may be:

- Full
- Partial

Refund flow:

Refund Request
↓
Validate Refundable Amount
↓
Provider Refund
↓
Verify Result
↓
Record Refund Transaction
↓
Update Payment
↓
Update Order

============================================================
47. REFUND IDEMPOTENCY
============================================================

Repeated refund requests must not create duplicate refunds.

Use:

- Internal refund ID
- Provider refund ID
- Idempotency key
- Amount validation
- Refundable balance

============================================================
48. REFUNDABLE BALANCE
============================================================

Refundable amount must be calculated from authoritative payment
transactions.

Never allow:

Refunded Amount > Captured/Paid Amount

unless a separately authorized adjustment model exists.

============================================================
49. PARTIAL REFUND
============================================================

Example:

Paid = 10,000
Refund 1 = 2,000
Refund 2 = 3,000
Remaining refundable = 5,000

The system must track every refund independently.

============================================================
50. ORDER REFUND COORDINATION
============================================================

Payment refund and Order refund states must remain synchronized
through reliable events and reconciliation.

Module 09 owns the Order refund lifecycle.

Module 12 owns payment refund transactions.

============================================================
51. PAYMENT REVERSAL
============================================================

Provider may reverse or fail a previously successful payment.

The system must support:

- Reversal
- Chargeback/dispute foundation
- Provider correction
- Reconciliation

Financial state must not rely on assumptions.

52. DISPUTES / CHARGEBACKS

59. PAYMENT ERROR MODEL
============================================================

Normalize provider errors into safe platform categories.

- INVALID_REQUEST

- PROVIDER_UNAVAILABLE

- PAYMENT_EXPIRED
- AMOUNT_MISMATCH
- CURRENCY_MISMATCH
- SIGNATURE_INVALID
- DUPLICATE_REQUEST

Customer messages should be understandable without exposing

============================================================
60. PROVIDER OUTAGE
============================================================

If a gateway is unavailable:

- Mark provider availability appropriately
- Prevent unsafe payment attempts
- Allow alternative configured methods
- Preserve order/cart state
- Notify operations if necessary

Do not automatically switch payment providers unless an explicit
safe routing policy exists.

============================================================
61. PAYMENT TIMEOUT
============================================================

A gateway timeout does not necessarily mean payment failed.

State should become something such as:

PENDING / VERIFICATION_REQUIRED

until verified.

This prevents accidental duplicate charging.

============================================================
62. UNKNOWN PAYMENT STATE
============================================================

If provider response is ambiguous:

Do not assume failure.

Create reconciliation/verification work.

This is especially important for network timeouts after payment
submission.

98. FINAL ARCHITECTURAL RULES
============================================================

1. One Core Payment Engine.
2. Payment providers must use a common abstraction.
3. Store payment configuration must be tenant-scoped.
4. Client-submitted payment amounts must never be trusted.
5. Currency must always be server-validated.
6. Order total must be server-authoritative.
7. Payment status and Order status are separate concerns.
8. Payment attempts must preserve historical failures.
9. Transactions should be immutable financial records.
10. Provider references must remain separate from internal IDs.
11. Customer redirects are never authoritative payment proof.
12. Provider webhooks/callbacks must be securely verified.
13. Webhook processing must be idempotent.
14. Duplicate captures and refunds must be prevented.
15. Payment timeout must not automatically mean failure.
16. Unknown payment states must be reconciled.
17. Refunds must never exceed the refundable balance.
18. COD collection must be independently recorded.
19. Bank-transfer confirmation must require authorized verification.
20. Payment credentials and secrets must never reach clients.
21. Raw card credentials must never be stored by the core platform.
22. Provider accounts must never cross tenant boundaries.
23. Financial records must remain auditable.
24. Reconciliation is mandatory for externally processed payments.
25. Payment notifications must not determine financial truth.
26. Payment failures must not corrupt Order or Inventory state.
27. Payment operations must support reliable failure recovery.
28. New providers must be addable without rewriting Checkout.
29. Package entitlements may control gateway availability.
30. Payment architecture must remain ready for cards, wallets,
    tokenization, subscriptions, disputes, BNPL, and future
    payment technologies.
