ARCHITECTURAL PRINCIPLE
-----------------------
One Core Platform + Many Isolated Stores + Central Entitlement System +
Provider Adapters + Versioned APIs + Controlled Extension Framework.

This document defines the logical technical architecture. Exact framework,
runtime and infrastructure choices shall be confirmed against the existing
repository during the repository inspection phase. The architecture must
avoid unnecessary technology changes merely for preference.

====================================================================
1. ARCHITECTURE OBJECTIVES
====================================================================

The architecture shall optimize for:

1. Strict multi-tenant isolation.
2. Security by default.

9. Observability.

3. ARCHITECTURAL STYLE
====================================================================

Recommended baseline:

- Modular monolith initially where practical.
- Clear domain/service boundaries.
- API-first contracts.
- Background workers for asynchronous processing.
- Provider adapter pattern for external services.
- Event-driven extension points.
- Outbox/inbox patterns where reliability requires them.
- Centralized authentication and authorization.
- Centralized entitlement evaluation.
- Tenant-aware repositories/services.
- Configuration registry.
- Observability infrastructure.

The system should NOT prematurely become a distributed microservice system.
Services may be extracted later when scale, ownership, reliability or
operational requirements justify extraction.

6. MULTI-TENANT ARCHITECTURE
====================================================================

Tenant resolution shall occur before tenant-owned application operations.

Recommended request flow:

Request
 -> Edge/WAF
 -> Authentication
 -> Tenant Resolution
 -> Tenant Membership/Context Validation
 -> Authorization
 -> Entitlement Check
 -> Application Use Case
 -> Tenant-Aware Domain Operation
 -> Data Access
 -> Audit/Telemetry
 -> Response

Tenant context must be immutable for the duration of a sensitive operation.

Every repository/query that can access tenant data must receive or derive
validated tenant context.

Defense in depth should include:

- Application-level tenant filters
- Repository-level safeguards
- Database constraints/policies where practical
- Tenant-aware cache keys
- Tenant-aware queues
- Tenant-aware object storage
- Tenant-aware search
- Tenant-aware analytics

====================================================================
7. TENANT DATA ISOLATION MODEL
====================================================================

Preferred logical model:

Most tenant-owned tables contain a tenant/store ownership key.

Examples:
- tenant_id
- store_id
- created_by
- updated_by

Exact schema naming must be confirmed during database design.

Tenant-scoped unique constraints must use the appropriate tenant key.

Examples:
UNIQUE(store_id, sku)
UNIQUE(store_id, slug)
UNIQUE(store_id, coupon_code)

Global entities such as platform packages may remain platform-scoped.

====================================================================
8. REQUEST CONTEXT
====================================================================

A request context should contain, as applicable:

- Request ID
- Correlation ID
- User ID
- Tenant ID
- Store ID
- Role/permission context
- Package/entitlement context
- Locale
- Currency
- Time zone
- Client/application ID
- Authentication method
- Security classification

Sensitive context must not be exposed unnecessarily.

====================================================================
9. AUTHENTICATION ARCHITECTURE
====================================================================

Supported mechanisms may include:

- Session authentication for web applications
- JWT where appropriate
- OAuth 2.0/OpenID Connect integration where required
- API keys
- Service credentials
- Webhook signatures

Authentication must be separated from authorization.

Authentication answers:
"Who are you?"

Authorization answers:
"What may you do, and to which object/store?"

====================================================================
10. AUTHORIZATION ARCHITECTURE
====================================================================

Authorization layers:

1. Authentication
2. Platform role
3. Tenant membership
4. Store membership
5. Permission
6. Object ownership
7. Field-level restriction
8. Package entitlement
9. Resource/usage limit
10. Security policy

Example:

Authenticated User
 -> Member of Store A
 -> Has Order.Read
 -> Order belongs to Store A
 -> Package allows required capability
 -> Request permitted

Never authorize solely because a user is authenticated.

15. TRANSACTIONAL COMMERCE FLOW
====================================================================

Recommended checkout flow:

1. Load cart.
2. Validate tenant/store.
3. Authenticate customer where required.
4. Re-read products.
5. Re-check product status.
6. Re-check inventory.
7. Recalculate prices.
8. Evaluate promotions.
9. Calculate shipping.
10. Calculate tax if applicable.
11. Calculate final total.
12. Create/reserve inventory.
13. Create payment intent/attempt.
14. Persist order in correct state.
15. Commit transaction boundaries safely.
16. Process provider interaction according to adapter design.
17. Confirm payment through trusted provider signal.
18. Update order/payment state.
19. Trigger asynchronous notifications/events.

Browser redirects must not be treated as authoritative payment confirmation.

====================================================================
16. ORDER STATE MACHINE
====================================================================

Order states should be explicit.

Illustrative lifecycle:

Draft
 -> PendingPayment
 -> PaymentProcessing
 -> Paid
 -> Processing
 -> Shipped
 -> Delivered

Alternative paths may include:

PaymentFailed
Cancelled
Returned
RefundPending
PartiallyRefunded
Refunded

Actual states must be defined by Module 09 and payment/shipping rules.

Invalid state transitions must be rejected.

====================================================================
17. INVENTORY CONCURRENCY
====================================================================

Inventory reservation should use safe concurrency control.

Potential approach:

Available = OnHand - Reserved

Checkout:
- Lock or atomically update inventory.
- Verify availability.
- Create reservation.
- Associate reservation with cart/order.
- Expire/release reservation safely.
- Convert reservation into final stock movement after successful order state.

The implementation must be tested under concurrent checkout scenarios.

49. SCALING PATH
====================================================================

Stage 1:
Single application + relational database + cache/queue as needed.

Stage 2:
Separate worker processes + object storage + CDN.

Stage 3:
Dedicated search + stronger cache + database optimization/read scaling.

Stage 4:
Multiple application instances + load balancing.

Stage 5:
Service extraction for proven bottlenecks.

Stage 6:
Multi-region architecture where business scale justifies it.

Scaling decisions must be evidence-driven.

51. CODE ORGANIZATION RULES
====================================================================

Each domain should have clear separation between:

- Entities
- Value objects
- DTOs/contracts
- Commands
- Queries
- Services/use cases
- Policies
- Repositories
- Controllers/endpoints
- Validators
- Events
- Integration adapters
- Tests

Avoid a single giant service/controller containing unrelated domains.

====================================================================
52. INTEGRATION ADAPTER RULE
====================================================================

External providers must be hidden behind internal contracts.

Example:

IPaymentProvider
IShippingProvider
INotificationProvider
IAIProvider
IDomainProvider
IStorageProvider

Business logic calls the internal interface.

Provider-specific code remains inside an adapter.

This permits provider replacement without rewriting core commerce logic.

====================================================================
53. DATA MIGRATION ARCHITECTURE
====================================================================

Every schema change must have:

- Versioned migration
- Forward path
- Compatibility analysis
- Rollback/recovery consideration
- Test migration
- Production migration plan

For large datasets, migrations should be designed to minimize locking and
downtime.

54. IMPORT / EXPORT ARCHITECTURE
====================================================================

Import:

Upload
 -> Validate
 -> Parse
 -> Preview
 -> Validate business rules
 -> Approve/execute
 -> Transactional chunks
 -> Report results

Export:

Authorize
 -> Create export job
 -> Tenant-scoped query
 -> Generate file
 -> Secure storage
 -> Expiring access
 -> Audit

Large operations should be asynchronous.

====================================================================
56. FAILURE HANDLING
====================================================================

External failures shall use:

- Timeouts
- Retries where safe
- Exponential backoff where appropriate
- Circuit-breaker concepts where useful
- Dead-letter handling
- Fallbacks
- Clear user state
- Monitoring

Never retry a financial operation blindly without idempotency protection.

69. ARCHITECTURAL NON-NEGOTIABLES
====================================================================

1. Never bypass tenant isolation.
2. Never trust client-authoritative financial values.
3. Never trust client-authoritative permissions.
4. Never trust client-authoritative inventory state.
5. Never use package UI hiding as authorization.
6. Never expose secrets.
7. Never silently cross tenant boundaries.
8. Never allow third-party apps unrestricted access.
9. Never treat browser payment redirect as final payment truth.
10. Never process duplicate webhooks as duplicate business actions.
11. Never perform destructive production operations casually.
12. Never make a major rewrite before repository inspection.
13. Never hide test failures.
14. Never suppress security findings without documented justification.
15. Never let themes contain privileged business logic.
16. Never let AI bypass server-side authorization.
17. Never let support tools bypass security controls.
18. Never allow predictable object IDs to substitute for authorization.
19. Never let analytics become transactional truth.
20. Never allow cache/search/export systems to bypass tenant authorization.
21. Never commit credentials.
22. Never log sensitive credentials.
23. Never create financial records without traceability.
24. Never mutate historical invoices/orders without explicit policy.
25. Never introduce provider-specific logic into core domain rules.
26. Never create package-specific code forks.
27. Never remove data during downgrade unless documented and authorized.
28. Never expose private media through uncontrolled public URLs.
29. Never retry payment/refund operations without idempotency.
30. Never call an architectural change complete without verification evidence.

71. FINAL ARCHITECTURAL STATEMENT
====================================================================

The Umar Techy E-Commerce Platform shall be implemented as one coherent,
secure, modular, tenant-isolated SaaS platform.

The architecture deliberately starts with strong modular boundaries rather
than unnecessary microservice complexity. Provider adapters, APIs, events,
configuration, entitlements and extension points provide controlled paths
for future growth.

All implementation agents, including Claude Code, must use this architecture
together with the Project Bible, SRS and Module Blueprints. Repository-specific
facts discovered during inspection may refine implementation details, but
must not silently weaken the core architectural principles.
