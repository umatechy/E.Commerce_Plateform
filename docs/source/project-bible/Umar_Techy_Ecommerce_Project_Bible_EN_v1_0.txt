This Project Bible defines the permanent product, business, architectural,
technical, security, design, development, testing, operational and future-
expansion principles for the Umar Techy E-Commerce Platform.

It is the central project reference that connects the URS, SRS, technical

2. PRODUCT IDENTITY
====================================================================

Product Name:
Umar Techy E-Commerce Platform

Product Type:
Multi-Tenant E-Commerce SaaS Platform

Platform Owner:
Umar Techy

Primary Business Model:
Software-as-a-Service for independent e-commerce stores and businesses.

Core Concept:
One shared, continuously evolving platform serves many independent stores.
Each store operates as an isolated tenant while using the same core software,
platform infrastructure, security model and feature architecture.

Commercial Packages:
- Basic
- Business
- Premium

Packages are entitlement configurations on the same core platform.
They must never become separate codebases or forks.

4. CORE BUSINESS PRINCIPLES
====================================================================

4.1 One Platform
The platform is one product and one core architecture.

4.2 Many Tenants
Multiple independent stores operate on the same platform.

4.3 Isolation by Default
Tenant isolation is a mandatory security property, not an optional feature.

4.4 Stable Store Identity
Upgrading or downgrading a package must preserve Store ID/Tenant ID and
existing business data.

4.5 Entitlement-Driven Packaging
Package differences are implemented through feature entitlements, quotas,
limits, usage policies and configuration.

4.6 Server Authority
The server is authoritative for permissions, pricing, entitlements, stock,
order totals, payment state, financial state and security-sensitive actions.

4.7 Configuration Over Forking
Branding, themes, layouts, animation profiles and configurable behavior must
prefer configuration and reusable components over copied code.

4.8 Safe Evolution
The platform must evolve without unnecessary breaking changes or destructive
operations.

====================================================================

The database architecture must support:

- Tenant-aware data ownership
- Referential integrity
- Appropriate indexes
- Unique constraints scoped correctly
- Audit fields
- Soft deletion where justified
- Immutable historical records where required
- Safe migrations
- Transactional integrity
- Concurrency control
- Idempotency support
- Data retention policies

- Product SKU
- Category slug
- Product slug
- Customer identifiers
- Coupon codes
- Store configuration keys

12. API PRINCIPLES
====================================================================

- Tenant-aware
- Authenticated where required
- Authorized
- Versioned
- Documented
- Observable
- Rate-limited
- Idempotency-aware where needed

====================================================================
16. ORDER PRINCIPLES
====================================================================

Orders must preserve historical truth.

Once an order is placed, critical historical information must remain available
even if the underlying product, customer profile, shipping settings or store
configuration later changes.

Order totals must be server-calculated.

Order state transitions must be explicit and validated.

Important order events should be auditable and observable.

====================================================================
17. PAYMENT PRINCIPLES
====================================================================

Payment architecture must use provider adapters.

The core platform must not become tightly coupled to one gateway.

The design must support future providers such as:

- Local Pakistani gateways
- Bank/payment integrations
- International gateways where legally and technically supported
- Cash on delivery
- Manual payment workflows where appropriate

Never store raw card data unless the entire architecture and compliance model
explicitly supports it. Prefer provider-hosted/tokenized payment flows.

Payment webhooks must be authenticated, verified, idempotent and replay-aware.
